# Reset a website's native analytics

In **Collection and privacy**, an owner or admin can open **Reset analytics**, check the website name, and type `RESET` exactly. Unsaved collection settings must be saved or cancelled first. Nothing resets while typing or opening the form. Delete website is a separate, unimplemented P46 action.

Reset makes native observations before one database acceptance instant permanently unavailable: native events/revenue activity, observed visitor activity, current session properties, identity links, performance, replay content and numeric heatmap observations/background associations. Collection settings, public tracking key, website identity, authored definitions/notes/boards/reports, provider/import results, provider requests/charges, tracked links/pixels and other projects are preserved. It does not revoke installation/user credentials or imply that historical visitor hashes have changed.

The native project epoch rotates. Old consent/basic collection proofs and replay/heatmap capabilities are refused; an old signed browser context no longer extends its earlier visit. The existing project/month visitor hash is unchanged. Cookieless collection can resume when the tracker reads the current policy; consent-first collection requires current permission. This does not reinstall tracking or manufacture traffic.

## Wire and authority

`GET /api/projects/:projectId/analytics-reset` returns `{projectId,name,role,revision,retainedFrom,cleanup}` for current owner/admin only. `retainedFrom` is null or the exact SQL boundary with six fractional digits; `cleanup` is `pending|complete`. No query/body, API key or public share grants this operation.

`POST` to the same URL requires same-origin browser sign-in and strict JSON (1024 UTF-8 bytes maximum): `{requestId:<UUID>,revision:<current analytics revision>,confirmation:"RESET"}`. Missing/extra fields, stale revision and nonexact confirmation refuse. The existing origin/CSRF admission applies. Current owner/admin membership is checked after workspace UPDATE then project UPDATE gates, before receipt replay.

One READ COMMITTED transaction takes a fresh SQL clock **after** admission, advances the four existing irreversible native watermarks, rotates `analytics_epoch`, increments `analytics_revision`, schedules cleanup and records the bounded ACK in `project_content_request`. The operation namespace is `analytics.reset.v1`; canonical receipt input includes actor ID and the complete strict body. An existing context/analysis UUID cannot collide into reset. Same UUID with another actor/body/operation refuses409. A genuine exact retry returns the original `{projectId,requestId,appliedRevision,cutoff}` ACK, current state and `replayed:true`, without moving any cutoff or epoch again. Receipt persistence failure rolls the entire mutation back. No schema, migration, dependency, provider call or new queue is needed.

The pool acquisition bound remains5s; transaction timeout15s, statement5s and lock2s. The client stops waiting after15s. A lost/timed-out reply means an unknown outcome: retain its UUID/revision/body and explicitly retry only that request after fresh access reload. GET is current state, not acknowledgment of an unknown POST. A decoded denial after timeout cannot sign the user out; stale identity/route/access replies cannot publish or invalidate a replacement owner. Same-identity parent lease changes retain the pending request ref; project/account replacement disposes it.

## Erasure and publication

ACK means the cutoff committed, **not** that disk cleanup completed. The HTTP request performs no deletion loop and starts no worker. The existing worker uses its existing bounded native batches (1000 events,1000 performance rows,32 replay chunks up to8MiB,64 heatmap batches up to2MiB,1000 profile/link rows per pass). Reset freezes its acceptance instant as the project's cleanup target under the current policy revision, so the existing worker erases everything before it in its bounded batches while the irreversible watermark already keeps that range unavailable; a policy revision during cleanup replaces the frozen target like any other, and the watermark never moves backwards. Its provider raw/derived cutoffs and provider expiry calls remain unchanged; reset never supplies its acceptance time as a provider-retention cutoff. Worker retries keep the normal schedule/error path. Fresh native observations at/after the boundary survive. Visitor first/last bounds are recalculated only from retained observations. Session-property cutoffs and worker boundaries stay SQL text, never JS-rounded dates.

Read and reset transactions linearize at the existing workspace gates. Website share reads are the one exception: they take no gate, compare the epoch read before the aggregate with a recheck before COMMIT and answer 503 when it changed, so every reset must keep rotating `analytics_epoch` in the same commit as its cutoff (see [website-shares.md](website-shares.md)). A native read that owns SHARE first can finish as an earlier read before reset obtains UPDATE; bytes already sent cannot be retracted. Reads admitted after reset see the new watermark. Plain Analytics uses the same read gate as the other native readers. Raw Events waits on that gate, releases it, then reads under the project SHARE lock alone, so an in-flight reset still precedes its population while key revocation and membership writes land during the read and the final authority check applies them (`docs/native-api-authority.md`). Ordinary Explorer retains its original resolved-cohort REPEATABLE READ snapshot, releases it, then takes a fresh workspace/project SHARE transaction and compares current membership plus exact watermark/epoch before returning any report/CSV; a changed boundary refuses409. This preserves the existing concurrent cohort-definition snapshot oracle. Borrowed board reads retain their existing current binding gate.

Replay/heatmap request tombstones, event/identify deduplication metadata and authored saved labels can remain for their existing bounded retry/retention lifetime; hidden content cannot be revived by extending a retention policy. Cleanup status excludes these retry tombstones. The form reports accepted cutoff and bounded cleanup separately. It makes no claim to erase data already exported, held by another browser or stored in unrelated provider reports.

The separately versioned auxiliary export hunk adds `analytics_epoch` to both existing first/final gate reads and their exact equality check; its existing SHARE gates, microsecond watermark, arithmetic, ZIP bytes and fresh clocks stay unchanged. That file is a later composition dependency, not present in this schema60/850 source basis.

Replay and heatmap Begin INSERTs use one materialized SQL clock each for exact created_at and the existing duration/drain deadlines. Millisecond wire/token values stay unchanged. The native fixed-clock case replaces only those two INSERT clock expressions, executes real PostgreSQL, proves millisecond truncation would fall below a nonzero-microsecond cutoff, refuses old capabilities and accepts the fresh post-cutoff uploads. It does not claim wall time advanced.

The original native-identify fixed-time test seam now matches its new shared SQL clock prefix and provides matching exact ISO6 accepted_at; all original 24-hour and month-boundary assertions are retained.
