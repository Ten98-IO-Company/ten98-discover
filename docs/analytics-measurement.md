# Native analytics measurement contract

This is the measurement contract for native collection and its remaining analytics extensions, not evidence of full V1 completion. P28–P40 remain subject to the [parity acceptance gates](https://wiki.ten98.io/s/ten98-docs/p/parity-1fPLxG5kX5). The [foundation runbook](foundation.md#native-collection-and-measurement) identifies implemented behavior and checks. This contract keeps native observations, estimated visitor identity and imported provider measurements distinct.

## Identity and visits

An analytics visitor is a project-scoped pseudonymous estimate, never an application login or a unique person. The server derives its key from a trusted client IP, User-Agent, UTC calendar month and, for consented collection only, an optional explicit distinct ID using a domain-separated keyed hash. Cookieless basic observations use a separate hash namespace and cannot acquire a later consented profile. Neither the IP, raw User-Agent nor raw distinct ID belongs in the event or visitor record. Hashing does not make these measurements anonymous.

Changing project, network address, browser identifier, distinct ID, month or server signing secret changes the visitor key. Shared network/browser characteristics may combine visitors; changed characteristics may split one visitor. Distinct IDs are untrusted observations: they cannot authorize access or merge application accounts. A later explicit identification does not rewrite earlier anonymous events.

The metric version `umami-3.4-hour-cache-v1` preserves the pinned reference's hourly-derived visit behavior:

- Without a valid context, derive the visit from the visitor key and current UTC hour.
- A signed browser context binds project, visitor, visit and its original issuance time. It can carry a visit across an hour for at most 30 minutes from issuance; accepted events do not slide that timer.
- At exactly 30 minutes the context remains valid; after that it is replaced. Replacing it within the same hour can yield the same visit key.
- Monthly visitor rotation overrides even a younger context. Future, malformed, tampered, foreign-project and mismatched-visitor contexts are ignored.
- Missing trustworthy network identity or usable User-Agent yields no visitor/visit key. A previously valid context cannot bypass that requirement.

For example, a visit beginning at 09:50 can continue at 10:15 with its original visit key. It expires after 10:20. A context beginning at 10:00 and replaced at 10:31 can retain the same hourly visit key. These are not conventional sliding inactivity sessions. Browser context stays scoped to one project/endpoint/environment; no alias or workspace grouping creates cross-site identity.

The pinned source is [Umami 3.4.0 collection](https://github.com/umami-software/umami/blob/ec0ff50388c264ed8ce46f00967e92f7e71476ae/src/app/api/send/route.ts#L154). Ten98 uses explicit UTC periods and a separate native metric version rather than promising numerically identical reports across every upstream deployment configuration.

## Network boundary

`ANALYTICS_NETWORK_MODE` defaults to `off`. In `direct` mode, identity uses only the original Node transport's socket peer. In `proxy` mode, the socket peer must be in the explicitly configured `ANALYTICS_TRUSTED_PROXIES` IP/CIDR allowlist. The bounded `X-Forwarded-For` chain is examined from right to left, stopping at the first untrusted address. Missing, malformed or entirely trusted chains remain unknown.

Only bare IP literals are accepted. Ports, quoted addresses, zone identifiers and hostnames are rejected. IPv4-mapped IPv6 forms normalize to the same IPv4 address. A plain or cloned Fetch `Request` may lack transport metadata; client headers must never substitute for it.

`ANALYTICS_EXCLUDED_IPS` is one installation-wide list of at most 32 IPs or CIDRs (4096 characters, the same entry rules as the trusted proxies), like pinned Umami's [`IGNORE_IP`](https://github.com/umami-software/umami/blob/ec0ff50388c264ed8ce46f00967e92f7e71476ae/src/lib/detect.ts#L150), with no per-website field; it is named in the network family rather than `IGNORE_IP` because its semantics differ. It is matched only against the address the network mode resolves: the socket peer in `direct` mode, or the first untrusted address from the right of a trusted chain in `proxy` mode. Forwarding headers can never trigger it, because only that address (in `proxy` mode the one the trusted edge appended) is matched. An unknown address is never excluded: no transport peer, an untrusted proxy peer, or a malformed, fully trusted or over-long chain (more than 20 entries or 4096 bytes). So in `proxy` mode behind an edge that appends to a client-supplied `X-Forwarded-For`, a client that sends a malformed or over-long header leaves its address unknown and is collected; this includes the `unknown` token some forward proxies send. A client can opt itself back in but can never exclude anyone, so this is a data-quality filter, not access control. A non-empty list with `ANALYTICS_NETWORK_MODE=off` resolves no address and is refused at startup with the same redacted configuration error, as is an invalid entry or more than 32 entries. Umami instead always derives an address from `payload.ip`, a CDN header or the leftmost `X-Forwarded-For` (so any client can trigger or bypass its list), skips malformed entries and client addresses silently, has no size bound and compares exact strings plus same-family CIDRs. Entries are canonicalised, so IPv4-mapped IPv6 forms fold to IPv4 and a native IPv6 address never matches an IPv4 rule. An excluded request is answered like other refusals: browser events, identify and performance get `202 {accepted:false,reason:'collection_disabled'}`, the same reason as DNT, GPC, bots and disabled collection (Umami's `/api/send` answers 403), replay and heatmap uploads get their existing 403 (like Umami's `/api/record`), and tracked links and pixels still redirect or return their image while recording nothing (as Umami's pixels and links do). The origin check still answers first, and exclusion outranks a missing grant. Umami returns its bot response and resolves geography before the address check; excluded requests here derive no identity and perform no geography lookup or write. The list and any matched address are never stored, logged, returned, exported or published in the public tracking configuration. Vendor destinations loaded in the browser are not suppressed. Changes need a restart and are not retroactive; a rollback to an image without this setting counts that traffic again. Shared NAT, CGNAT or VPN ranges (or `0.0.0.0/0`, `::/0`) exclude unrelated visitors of every workspace and website on the installation.

Direct mode behind a shared gateway can collapse visitor estimates, so it must not be selected automatically. Proxy mode needs a verified deployment topology and an edge that overwrites/appends forwarding headers correctly. Development proxy behavior does not establish production Nitro, Docker or Caddy behavior. Those paths require real transport tests before documentation claims support.

## Collection and privacy

Native analytics has its own collection policy, independent of vendor destinations. New projects default to `collectionMode: cookieless`; missing modes in existing settings remain `consent-first`, and old settings writers preserve the current mode. Basic events can start without a grant under a current cookieless policy. Explicit refusal, Do Not Track, Global Privacy Control, disabled collection, excluded paths, recognized bots and an excluded network address still block collection. Consent-first events and every identify call require an explicit current analytics grant. Advertising and other vendor purposes remain separately consent-gated.

Public configuration schema3 exposes the effective mode and existing combined epoch for at most60 seconds. Browser events carry exactly one current-policy envelope: `collection:{mode:'cookieless',epoch}` or `consent:{analytics:true,epoch}`. Basic events cannot contain an explicit distinct ID or an identify variant. The server records `event.collection_basis` as cookieless or consent; pre-upgrade/API observations remain NULL, not inferred history. API-key ingestion excludes both browser envelopes and stays identity-free.

The SDK persists version2, site/origin/environment-scoped preferences only, not identity or collection context. An explicit `ten98.consent` refusal also opts out of basic collection and survives epoch/grant expiry. `ten98.setAnalyticsOptOut(boolean, siteOptions)` changes only basic refusal: clearing it cannot create, renew or revoke an existing enhanced grant. Unreadable/malformed preferences block basic collection. A later grant does not replay earlier activity or recount an already dispatched current-page observation, including an unknown receipt. Basis changes abort pending native work and clear context/identifier. Previously accepted records remain subject to retention; withdrawal does not retract them or guarantee a different future rotating key.

Dashboard collection basis counts describe retained recorded pageviews. Capture coverage is always unknown: rejected/blocked visits are not separately collected to invent a denominator. Retention completeness is different from total traffic coverage. Basic and consented keys can split one visitor estimate; full Umami parity, anonymity and legal consent exemption are not claimed.

The server checks the current combined native/destination consent epoch before accepting browser events. Policy publication and collection must share a project lock, with the effective destination revision read in a fresh statement after acquiring that lock. This prevents a waiting request from accepting an old policy snapshot after publication commits.

Referrer, campaign and screen capture are separately configurable and default off. Campaign capture reads the five `utm_*` values and, only for events that carry the analytics grant, the six ad click identifiers pinned Umami stores (`gclid`, `fbclid`, `msclkid`, `ttclid`, `li_fat_id`, `twclid`; owner decision D1) from the current page URL for every page view and custom event, never for performance metrics. Values are read like `URLSearchParams.get` (case-sensitive key, first occurrence, empty kept) when each event is sent and are not sticky, as in Umami. The tracker and the collector cut each identifier to 255 code points, and the tracker skips a value containing NUL so the event itself is kept. Cookieless basic events and API observations never store click identifiers. They are kept in their own event columns, never in the dimensions JSON, visitor keys, identity links, filters, grouping or exports; only [attribution](attribution.md) reads them, as a closed Paid ads label. DNT, GPC and refusal stop them with the event. Referrer capture stores the hostname only. The first page view a site sends in each tracker identity generation is its landing view and carries the origin of `document.referrer`, even when consent or configuration arrives only after an in-app navigation. `identify` with a new ID, `resetIdentity`, a consent basis change or a withdrawal starts a new generation and so a new landing view, so a key that changes mid-document is credited with the external referrer; a view dropped before sending does not count. A generation only approximates the server’s visitor key: a rotation the browser cannot see (UTC month, IP or user agent) gets no landing referrer, and reports then show no referrer rather than the site. Each later page view for another path (after a `pushState`, `replaceState` or `popstate`), and the events after it, carry the previous sent in-app page's origin instead: a self-referral, as pinned Umami sends the previous in-app page on `pushState` and `replaceState` (it does not observe `popstate`; owner decision D11, 2026-10-17). Each configured site keeps its own switch. Only an http(s) referrer origin is sent: a non-web referrer such as `android-app://` (an opaque origin in most browsers, a tuple origin in Chrome on Android) would make the collector refuse the whole event. Only the origin leaves the browser, so the self-referral is the site’s own host. It is stored like any host, as are the self-referrals that internal links on multi-page sites already produce, but reports never credit it: the channel projection, [attribution](attribution.md) touches and [revenue](revenue.md) sources treat a referrer equal to the event’s own host, ignoring a leading www. on both sides, as no referrer, as pinned Umami does; unlike Umami, other aliases such as verified serving domains are not matched. The referrer dimension in Explorer, comparison, realtime and export still lists it literally. `tests/tracker.test.ts` pins the views. Query strings and fragments remain excluded from the native event path; only the allowlisted campaign values above are extracted. Language is normalized. The explicit custom-property API must not scrape personal data from forms; it is not a guarantee that arbitrary caller-supplied properties contain no personal information.

The overview **Top referrers** card lists up to 20 external referrer hosts among the selected range's page views after every overview filter, ranked by estimated visitors when any row is measured, otherwise by page views, with page views and then the host's bytes (`COLLATE "C"`) as tie-breaks; Umami orders by its count only. It omits self-referrals (the rule above, applied at read time; Umami drops them at ingest and again in its query), page views without a recorded host and stored non-string or out-of-bound values (which are skipped rather than refusing the report). Hosts are listed literally: no www. folding and no punycode decoding, while pinned Umami strips www. at ingest and decodes punycode for display. Selecting a host filters every report by the literal referrer, as Umami's row filter does; because that filter is literal, in a project with several origins it can also match that host's own in-site views. The card's page views plus the self-referrals plus the page views without a host equal the total; Explorer, comparison, realtime and export keep the literal referrer dimension. Umami's Sources panel shows 10 rows by distinct sessions over every non-custom event type, with a Channels tab, favicons, outbound links, percentage bars and a 500-row More view; this card counts page views only and has none of those (channels stay in comparison and Explorer, the content security policy blocks external icons, and Explorer grouped by referrer is the full list). Umami always captures referrers; here data exists only where referrer capture is on, which is off by default, so the card explains that capture is optional.

Property input is bounded, typed and validated before persistence. Missing, null, empty string, number and numeric-looking string remain distinguishable. Dotted and backslash-containing keys cannot collide with nested paths. Invalid date-looking strings remain strings. NUL and malformed Unicode are rejected because PostgreSQL JSONB cannot preserve them.

API-key ingestion remains authorized per workspace and project and respects collection disablement/path exclusions; it is not matched against `ANALYTICS_EXCLUDED_IPS` (Umami has no separate keyed ingestion path). An API observation cannot claim browser consent or acquire a browser visitor merely by submitting a context or distinct ID. It is retained with its own source and identity coverage.

## Native identify and session properties

The browser SDK supports `ten98.identify(properties, siteOptions)` and `ten98.identify(identifier, properties, siteOptions)`. Options select exactly one configured site key, collector origin and live environment; an ambiguous selection fails without fanout. A top-level properties `id` is a compatibility shortcut consumed as the identifier and omitted from stored properties. An explicit identifier and shortcut must match. Nested `id` remains ordinary caller metadata, which may contain personal data.

Identify applies a typed patch to current session properties under the existing rotating visitor key. It creates no event, pageview, visit or event-based visitor first/last-seen record. Omitted keys keep their values and update times; null is a stored typed null. Each call and the accumulated retained profile are bounded to 50 keys. No raw identifier argument, IP or User-Agent is stored in the profile or identify receipt. A usable trusted network identity is still required, even with an identifier.

Consent, current configuration, native enablement, privacy signals and path exclusions apply before local identity assignment or dispatch. Pre-consent calls are discarded entirely. Identify does not invoke vendor pixels or their queues. A permitted explicit identity change takes effect synchronously for subsequent native events, clears context and aborts older native work. Both event and identify responses check the captured identity generation after response-body parsing. Identity remains only in memory. `ten98.resetIdentity(siteOptions)` clears that site's local identity and pending native work; it neither erases server data nor changes vendor identity. Withdrawal/configuration expiry also clears identity; regrant requires a new identify call.

The strict identify variant of `/api/collect` has an immutable UUID `requestId` and millisecond RFC3339 `sentAt`. A request is admissible for 24 hours from that timestamp and at most five minutes into the future. Exact normalized-body and visitor-key replay is a no-op, with no context refresh; changed operation/key reuse conflicts. An expired request returns a stable `request_expired` reason even after its receipt is cleaned up. Latest means server acceptance order, not timestamp or call order across tabs. The SDK has no automatic retry or retained replay queue: another identify call is a new update, and an unknown outcome does not prove rejection.

Session properties follow raw-analytics retention from each key's own latest accepted update; new traffic or sibling updates do not extend it. They have a separate monotonic cutoff and sticky evidence-loss marker. Saving a shorter policy immediately excludes expired values; later extension cannot restore them. Explorer and saved cohorts support current retained session-property conditions with separate snapshot, pre-selection identity candidates and property-loss metadata; see [Explorer](explorer.md#current-session-property-conditions). Policy, profile evidence and results use one data-statement snapshot after fresh workspace-gate authorization. Known property loss makes Missing unavailable, rather than a zero or lower bound. Persistent-person continuity and historical property values remain unavailable.

## Reports and coverage

### Browser, OS and device environment

Permitted native observations derive fixed browser and OS labels from the request User-Agent using `detect-browser@5.3.0`, and a device class using the MIT `ua-parser-js@1.0.41`. Derivation occurs after current collection policy accepts the event, for both basic and consented collection. It does not require network identity: pageviews can have environment labels while visitor/visit estimates remain unavailable. No extra SDK payload, capture switch or table is introduced. Public event and identify dimensions reject `browser`, `os`, `device`, `environmentVersion` and raw User-Agent fields; API-key observations cannot impersonate browser environment.

Only bounded family labels, a fixed device class and `environmentVersion: server-ua-environment-v1` enter the existing event dimensions. No raw User-Agent, IP, separate parsed browser/OS version fields, device model/vendor or client hints are added. Fixed detector OS labels such as `Windows 10` are labels, not an arbitrary parsed version. Empty, malformed or over-1024-character agents record `unknown`, not a guessed desktop. The v1 device parser internally truncates at 500 characters; for 501–1024 characters the device remains unknown even when browser/OS classification is available. An explicit known desktop OS and recognized browser family with no mobile/tablet/other device evidence yields `desktop`; ambiguous QNX, unknown browsers and bot/tool families do not. Only an already enabled and validated screen width of at most1920 yields the pinned Umami `laptop` heuristic. Width is not requested solely for classification and is not a hardware measurement.

Pinned Umami3.4.0 uses its own detector/device parser combination and laptop heuristic. This implementation pins the MIT v1 device parser; its newer AGPL/commercial v2 is not installed or copied. Device/browser results can differ and full parser parity is not claimed. User-Agent is visitor-controlled and classification is a best-effort observation, not proof of a physical device or person. Duplicate event IDs cannot rewrite the environment or receipt.

`GET /api/projects/:id/analytics` accepts one `browser`, `os` and/or `device` exact filter alongside the existing date range. Supported values come from the fixed shared catalogue; `unknown` selects attempted unrecognized classification and `not-recorded` selects missing historical/API evidence. Old records are not backfilled. Filters constrain the entire observations population: overview cards, daily buckets, page/custom-event rankings, visits and all three environment breakdowns. The same keys work in Explorer and saved-cohort qualification; additional field predicates support existing text and Missing/Exists operators. Funnel/goal exact filters share the same population SQL, while their existing unsupported cohort selection remains rejected.

The response `environment` object includes complete bounded `browsers`, `operatingSystems` and `devices` rows, filters, detector method/version and recorded/not-recorded pageview coverage for the selected retained population. Missing rows have `value:null`; attempted unknown rows use `value:'unknown'`. Each row returns pageviews, identified pageviews and nullable estimated visitors, visits, bounce rate and observed visit duration. Ranking uses estimated visitors descending (nulls last), then pageviews and a deterministic fixed-label tie break. Where identity is unavailable, pageviews remain nonzero and visitor/rate/time measurements remain null. Rows reconcile to selected retained pageviews. The same rotating estimate can appear in more than one category; summing category visitors does not give distinct people or even distinct period keys. A wholly expired range returns null coverage counts and no rows, not zero. Partial retention remains labelled by the existing report coverage. Recorded environment coverage does not establish total traffic capture coverage.

`tests/analytics-environment.test.ts` is the pure parser/input/binding check. `tests/analytics-environment-integration.ts` requires explicit `TEN98_INTEGRATION_TEST=1`, `TEN98_ENVIRONMENT_TEST=1`, network identity off and a fresh synthetic `ten98_environment_<12hex>` PostgreSQL database on loopback port55501 (or the workflow's isolated `ten98_environment_ci` database, migrated first); it exercises both collection bases, idempotency, real API-key spoof rejection, null identity, complete-population filter reconciliation, Explorer/cohort/goal callers and retention. It never uses an existing deployment database or calls paid providers. The increment is tracked in [issue114](https://github.com/Ten98-IO-Company/ten98-monitor/issues/114); local acceptance is not a release or live-deployment claim.

All accepted events retain their server receipt time. Public client timestamps cannot move observations into another reporting period. Event IDs remain idempotent per project; a duplicate cannot rewrite data, advance visitor timestamps or mint a replacement context.

Overview pageviews and custom-event counts remain available for legacy observations. Identity metrics describe only observations with valid visitor/visit keys; reports expose their coverage rather than inventing identity for historical rows. Unavailable measurements and rates with zero denominators are null, while a measured empty count is zero.

Overview visitors count distinct visitor keys and visits count distinct visit keys among qualifying pageviews. A bounce has one pageview and no custom event in that visit within the selected window. Observed visit duration is the interval between first and last pageviews; one-page visits contribute zero. Average duration divides the summed observed duration by qualifying visits. It does not measure active engagement or time after the last pageview. Daily distinct visitors cannot be summed to obtain period visitors. [Pinned overview calculation](https://github.com/umami-software/umami/blob/ec0ff50388c264ed8ce46f00967e92f7e71476ae/src/queries/sql/getWebsiteStats.ts#L42)

Cards, series, breakdowns and exports must use one explicit filter population. Event-property exploration must not silently present custom events as pageviews. Legacy page rankings retain the label pageviews; a distinct-visitor ranking must use a different explicit column label. Filtered bounce semantics require fixtures covering custom events outside a matching page filter.

Store UTC instants and use a named IANA timezone for calendar date ranges. Ranges are half-open: the start local midnight is included and midnight after the final local date is excluded. Generate local calendar buckets; daylight-saving days are not necessarily 24 hours. Comparisons must state whether they compare calendar periods or elapsed durations.

Future revenue and performance observations retain separate measurement rules. Revenue requires explicit currency and financial precision; generic numeric properties are not the authoritative revenue ledger. RUM samples do not become pageviews or custom-event bounce suppression. Each performance metric needs its own sample count and percentile calculation, with missing metrics remaining unavailable.

## Remaining acceptance evidence

Browser consent/withdrawal, encoded path exclusions, production Node transport, transactional policy-publication races, duplicate handling and tenant/API-key boundaries have local acceptance checks. The full release still requires actual proxy deployment tests, typed-property queries, DST boundaries, filtered metric reconciliation, identity links, advanced reports and the remaining parity rows. A conservative bot-name heuristic is not comprehensive bot detection. Imported provider visitors, reach and attributed conversions cannot be added to native distinct visitors as though they were one population.
