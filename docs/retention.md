# Retention

Workspace members can inspect retention. Owners can preview and explicitly save a policy. Durations are whole days from 1 to 3,650. A day is 86,400 seconds; cutoffs use UTC receipt time and delete rows strictly before the cutoff, retaining rows exactly on it.

| Category | Default days | Current storage and cleanup |
| --- | ---: | --- |
| Raw analytics | 90 | Events, their properties/dimensions, unreferenced visitor identities and current session properties, each property timed from its own latest accepted update |
| Replay | 7 | Recordings (stored as PostgreSQL chunk rows, not files), measured from creation; heatmap background references tied to an expired recording; request tombstones follow derived history |
| Raw provider evidence | 90 | Generated prompt answers/citations, copied execution input and completed manual redirect-chain observations, measured from completion; authored prompt versions and financial/idempotency receipts remain |
| Derived history | 365 | Finished Google import rows, Google quality metadata and normalized keyword results, measured from completion; original outcomes, used quotes, charge evidence and idempotency receipts remain |

All provider spending and request-deduplication records are preserved, including reserved, dispatched, uncertain, settled and cancelled requests. Authored project context, research notes, prompts and immutable versions, mutation receipts, reports, templates, shared snapshots, credentials, accounts, teams and configuration are also preserved. Replay content lives only in database rows, so there are no replay files to delete; the worker does not scan or delete arbitrary artifact files. This increment implements part of P31/P68, not complete retention/export/erasure parity.

## Preview and save

The preview estimates eligible event rows and their approximate logical size. It examines at most 10,001 candidates and labels a capped count as at least 10,000. Bytes describe the first 10,000 sampled rows; they are not a complete storage inventory or a promise of reclaimed filesystem space. Query timeouts appear as an unavailable estimate, never zero. Separate previews count eligible finished Google imports and keyword result payloads against the derived cutoff, and generated prompt answers, copied inputs and redirect observations against the raw-evidence cutoff. Each uses the same 10,001-candidate bound and explicit unavailable state. Replay has its own preview of recording metadata and chunk rows under the same bound.

Saving requires a preview bound to the exact policy, workspace, owner and current revision. It expires after five minutes. The API rechecks live ownership under the workspace lock. Stale or expired previews require a new preview; changing the draft invalidates the browser confirmation. The preview is advisory: data arriving after it may change the eventual eligible count.

Shorter periods permanently remove older observations. For events, extending retention stops the previous shorter target before the next batch but cannot restore deleted history; every pass moves the retained-history boundary to its target, so observations the shorter target had already made unavailable stay unavailable even where a later pass leaves their rows in place, and the boundary never moves backwards. A reset freezes its acceptance instant as the same kind of target under the current policy revision. Session properties have a separate irreversible cutoff latched at policy save from the prior and new periods: shrinking and then extending before cleanup cannot resurrect expired values. Their preview counts are separate, capped and unavailable on timeout. This app does not erase retained operator backups. Follow a separate private backup and recovery policy.

Identify receipts have a fixed protocol horizon of 24 hours from their immutable client `sentAt`, independent of workspace retention days. Cleanup removes only expired receipts; request-age validation prevents an old replay becoming a new update after cleanup. Project deletion cascades to profiles and receipts. Profiles can exist before any traffic, so they do not require an event-derived visitor record. Bounded cleanup marks prior evidence loss before deleting expired properties; new updates cannot clear that marker or refresh omitted properties.

## Worker and reporting

The existing worker attempts one project per ten-second tick, with at most 1,000 event deletions, 1,000 expired replay paths, 32 replay chunks (at most 8 MiB), 1,000 chunk-free replay metadata resets, 1,000 expired replay tombstones, 64 heatmap background references, 1,000 orphan visitor deletions, 1,000 expired session properties, 1,000 expired identify receipts, 20 expired Google imports (each at most ten pages), 100 keyword result payloads, 100 prompt results, 100 copied prompt inputs and 100 completed redirect observations in each transaction. It also removes at most 100 expired unused quotes from each research adapter. Workspace then project locks serialize policy changes, collection and provider result publication. A two-second statement timeout and a short lock timeout bound contention; failures roll back the batch and expose a redacted cleanup status. Cleanup does not enable provider schedulers. Shutdown waits for the active batch. A failure rolls back all cleaners together, and any remaining batch prevents a premature completed status.

Rows that name a closed dashboard account follow a separate instance-wide rule, not workspace policy: a daily pg-boss job deletes their financial and audit rows 7 years after creation and then removes unreferenced account tombstones, within a per-run cap. See [account closure retention](account-closure.md#retention).

Projects with pending work become eligible again after ten seconds; completed projects after an hour. This is a bounded maintenance cadence, not a deletion deadline under arbitrary load or an unavailable worker. Inspect failed-project status and database/worker health when cleanup falls behind. Latest completed project cleanup is not proof that every project has caught up.

Google snapshot cleanup retains the original status, counts, request ID and source; it marks the data expired and removes rows/quality metadata only for completed, partial, failed or denied imports. Queued/running imports are excluded. Expired data is unavailable rather than an empty successful result, and repeated requests return the original receipt. See [Google imports](google-reports.md). Keyword cleanup clears only normalized result payloads and marks them expired; used quotes, requests, reconciliation evidence and all financial ledger fields remain. An abandoned quote without a run can expire after 24 hours. See [keyword research](keyword-research.md).

Prompt cleanup expires generated answers/citations and copied execution input under the raw-evidence policy. Copied input becomes eligible only when every comparison child has finished before the cutoff; queued/running children prevent expiry. Old uncertain charges retain generation IDs, original key and actor bindings, route, exact financial evidence and idempotency receipts for reconciliation. Authored prompt versions remain. Expired payloads are null with explicit expiry flags; reconciliation does not restore them or resend a paid request. See [prompt execution](prompt-execution.md).

Manual redirect cleanup removes only the observed chain strictly before its completion-time cutoff, retaining the receipt, expected configuration, original check status and request ID. Active checks are excluded. Expired evidence is explicitly unavailable; a retained completed status is not a current health assertion. See [redirect checks](domain-redirects.md).

Replay cleanup is monotonic: each pass raises the project replay boundary to its cutoff, and a policy save latches the shorter of the old and new periods, so extending retention cannot revive expired recordings. Expired recordings read as unavailable immediately while deletion catches up. A pass clears the entry path, deletes chunks, resets chunk-free metadata, and deletes the recording tombstone once it is also past the derived-history cutoff. A project is not complete while replay work remains; rows are locked per batch, so repeated or interrupted passes are idempotent. See [session replay](session-replay.md).

Each successful raw-analytics batch records a monotonic history boundary. While a multi-batch pass is in progress, older observations are excluded from reports so partial deletion cannot be mistaken for a complete total. A later policy extension does not move this boundary backward. Daily buckets before it are unavailable rather than zero; a day crossing it is partial. Recent-event counts describe retained observations, never a lifetime total. Visitor first/last timestamps describe their remaining observations. Analytics event-ID deduplication lasts only while the event exists; financial request deduplication is preserved separately.

## Upgrade and verification

Migration 0013 adds policy defaults, cleanup state and supporting indexes; it does not delete rows. Existing workspaces receive the defaults above. After explicit migration, starting the updated worker activates automatic cleanup. Review the policy and maintain a verified backup before upgrading a deployment with existing analytics. Index creation occurs in the existing migration transaction, so allow a maintenance window for a large event table. Do not edit old migrations or reset database volumes.

Normal PostgreSQL vacuum makes deleted-row space available for reuse and generally does not shrink filesystem usage. The application never runs `VACUUM FULL`. See [PostgreSQL vacuum guidance](https://www.postgresql.org/docs/18/routine-vacuuming.html).

Checks: `node --test tests/retention.test.ts`; the isolated integration runner calls `runRetentionChecks({ownerId})` from `tests/retention-integration.ts` and `runRetentionCoverageChecks()` from `tests/retention-coverage-integration.ts`. Both require `TEN98_INTEGRATION_TEST=1` and a local synthetic PostgreSQL database. They cover batch/restart boundaries, rollback, live authorization, concurrent collection, protected records, estimates and unavailable/partial reporting.

The integrated Google/keyword check is `node --env-file=.env tests/google-retention-integration.ts`. It covers separate scoped preview counts, exact cutoffs, bounded shared batches and preserved financial receipts. The Google browser runner also checks both preview counts and unavailable estimates at desktop and 360px widths, with external traffic blocked.

`tests/prompt-execution-integration.ts` checks raw-evidence previews, bounded payload-only batches, rollback and reconciliation after copied input expires. `tests/session-replay-integration.ts` and `tests/replay-heatmaps-integration.ts` check replay batch bounds, restart, tombstones, boundary precision and heatmap reference expiry. `tests/retention-browser.ts` checks the shared retention screen at desktop and mobile sizes. These runners require isolated synthetic local databases; no live provider calls are needed.

`tests/native-identify-integration.ts` checks typed patches, replay/conflicts, current consent, own-key expiry, shrink/extension, atomic rollback and bounded profile/receipt cleanup. It requires `TEN98_INTEGRATION_TEST=1` and `TEN98_IDENTIFY_TEST=1`, with a fresh guarded `ten98_identify_*` database on local test port55501 (or the explicitly isolated hosted CI database). It must never run against a preview or deployment database.
