# Native analytics comparison contract

`GET /api/projects/:projectId/analytics` accepts the existing inclusive UTC `from`/`to` dates and browser, OS and device filters, plus one optional `compare=prev|yoy`. Without `compare`, its response has the same fields and saved-retention-watermark semantics as before. Current date ranges remain limited to 1–366 days; the shared Explorer date parser is unchanged. Unknown, repeated or empty comparison selectors return 400.

With a comparison, the current report remains at the response root and a versioned `comparison` contains the full baseline report, generation time, metric changes, calendar state and alignment metadata. Both periods use one aggregation statement and database snapshot, the same membership/API-key authority, environment filters, collection settings and saved retention watermark. The aggregation body is reused through a PostgreSQL lateral query. Comparison reads have five-second statement and lock timeouts; a timeout returns a recoverable 503. No jobs, tables, dependencies or paid requests are added.

`prev` means the preceding equal number of whole UTC days. Its exclusive end is the current start, so the periods never overlap. `yoy` shifts each **inclusive calendar endpoint** back one year, clamping February 29 to February 28, then reconstructs half-open UTC bounds. The derived baseline can have up to 367 days. For example, 2025-02-28 through 2026-02-28 is 366 days, while its 2024-02-28 through 2025-02-28 baseline is 367 days and overlaps the current period on one day. A baseline before 1970 returns a recoverable 400 instead of silently changing the selection.

`alignment` records both actual day counts, their maximum number of ordinal chart slots and the exact intersection in days. Each report retains its complete, actual-date daily series. Consumers must not zip/drop unmatched leap-year days or invent a zero for an absent slot. The browser-safe calendar helper and DTO live in `src/lib/analytics-comparison.ts`.

Count and duration changes contain a signed absolute difference and signed percentage relative to the baseline. A zero baseline leaves the percentage unavailable while preserving a known absolute difference. Visitor and visit values remain estimates; missing identity evidence is not fabricated as zero. Bounce changes use **percentage points**, with no relative-percentage field. All changes become null when either period has partial or unavailable retained history. Each period retains its own coverage, collection-basis counts and environment coverage; policy extension cannot revive a saved deletion watermark.

`calendar` describes each whole-day period as `complete`, `partial` or `future` against the common database generation time. Today is provisional; this is not a matched-elapsed-time comparison. `asOf` records report generation and final API-key expiry authority, not an additional event receipt-time cutoff or a guarantee that the retention worker has completed. The inherited reader continues to apply the saved watermark. A retained empty period yields zero page views/custom events; unavailable history yields null, and unavailable identity measurements remain null.

All current read roles, including Viewer, retain their existing workspace boundary. API keys require the existing analytics read scope, workspace and current issuer membership, with a fresh raw database-clock expiry/revocation check in the report statement. Missing or foreign projects remain 404; an unavailable key is 401. Raw identifiers, addresses and user agents are not returned by this endpoint.

## Reference and remaining scope

The flow follows Umami's two closed previous-period/previous-year choices and its dedicated comparison controls, metrics and chart hierarchy. Reference source is pinned at [`ec0ff50388c264ed8ce46f00967e92f7e71476ae`](https://github.com/umami-software/umami/tree/ec0ff50388c264ed8ce46f00967e92f7e71476ae): `src/components/input/WebsiteDateFilter.tsx`, `src/lib/date.ts` (`getCompareDate`), and `src/app/(main)/websites/[websiteId]/compare/{ComparePage,CompareTables}.tsx`. This implementation uses native UTC whole-day ranges rather than Umami's arbitrary minute-span shifting; it explicitly reports leap-day length differences, year-range overlap, retention gaps and estimated identities. No external source code was copied for this increment.

The optional backend dimension breakdown below covers18 collected dimensions. Its native selector/browser flow, the remaining reference dimensions and channel methodology, broader date presets, compound breakdown, dedicated UTM reports and other required P32/P30 parity work remain outstanding. The existing top-20 page and event lists remain unchanged. This is not full Umami parity or release readiness.

## Optional collected-dimension comparison

`dimension` requires `compare=prev|yoy` and accepts only `path`, `referrer`, `browser`, `os`, `device`, `country`, `region`, `city`, `language`, `event`, `campaignSource`, `campaignMedium`, `campaignName`, `campaignContent`, `campaignTerm`, `hostname`, `screen`, `channel`. Distinct ID and tag remain rejected rather than returned as fabricated empty reports. Hostname uses only recorded origin (www remains distinct, port/scheme removed), with no project-origin fallback. Recorded screen is physical width × height, preserves orientation and is missing when capture was disabled or stored dimensions are invalid. Channel uses the existing `recorded-channel-tags-v1` campaign-medium rules, then other tags, a recorded referrer other than the host of the event's own recorded origin (a self-referral, compared with the port dropped and a leading www. ignored, is not a referrer; the label stays `recorded-channel-tags-v1` and the refinement applies to stored events, saved segments, cohorts and boards on their next read) or `not_recorded`; this is not a full first-channel-per-visit/referrer classifier. A request without either new parameter preserves the previous response shape, including absence of `dimensionComparison` and `selection`.

`selection` is an encoded existing Explorer query, with literal exact filters or its existing `predicates` JSON representation. The selection permits `path`, `eventName`, `referrer`, `language`, the five campaign fields, `origin`, `hostname`, `screen` and `channel`, Match All, no event/session-property conditions, and `eq`, `exists`, `missing` field operators. Fields are unique across both representations. No user-supplied SQL identifiers or regular expressions are evaluated. Empty exact strings and literal `not-recorded` remain strings; missing uses the Explorer presence operator. Canonical selection is returned and must remain replayable within the20,000 encoded-character whole-query limit. Shared referrer exact/advanced/restored-draft bounds now match the existing normalized2048-character host limit.

One filtered-all-event materialized population feeds both existing period reports, their daily/cards/environment/geography tables, and the requested dimension. The fixed scalar projection is shared with Explorer without changing its missing/type representation, property grouping, top100 or timezone rules. Non-event dimension rows require at least one page view, rank estimated visitors descending then page views and a deterministic typed key, and retain matching custom events for observed bounce calculations. A visit spanning groups can appear in several groups; category visitor estimates do not sum to distinct people. With no identity evidence, visitor/visit/rate/duration values remain null, and page views provide the ranking fallback. `event` includes custom events only, ranks their count, and does not invent pageview-derived visitor or visit estimates.

Geography tie breaks use the existing canonical state/country/region/city key order. Event-only rows and absent event counterparts keep visitor and visit measurements null, even when the other report has keyed pageviews. Scalar dimensions permit stored strings or an absent SQL value; malformed stored JSON numbers, booleans, arrays, objects or explicit null cause a whole-report503 across either period's full selected population, including groups outside the top20. They are not stringified or relabelled as missing. This does not change Explorer's historical typed-value grouping or ordinary normalized collection.

Bounce retains the shared whole-window retained custom-event suppression: a retained custom event at `/b` in the same authorized visit suppresses a selected one-page `/a` bounce even when report filters exclude `/b`. Category duration still uses only matching page-view spans. This increment reuses the existing shared bounce helper and does not change that methodology.

`dimensionComparison` is versioned `native-dimension-comparison-v1` and contains the selected field, metric, canonical selection, method and independent `current`/`previous` periods. Each period carries actual range (including367-day derived year baselines), saved retention coverage, identified/unidentified pageview coverage, complete group count, returned count/page views, truncation and at most20 rows. Each row uses Explorer `{type,value}` keys: missing is `{type:"missing",value:null}`, while qualified geography uses the existing canonical key string. Each row includes its observed metrics, full other-period counterpart, and change. The full counterpart lookup occurs **before** either side's top20 selection. `present` describes retained group evidence, not lifetime presence; unavailable counterpart history makes presence and all counterpart metrics null. An absent retained category has zero event counts, but no fabricated visitor estimate when the other period has no keyed pageview coverage. Bounce/duration remain null without an observed visit.

On **both** lists, signed changes are Current minus Previous, with Previous as the percentage denominator. A previous-only group therefore has a negative event change when current event absence is known. A zero baseline keeps the known absolute change but null percentage. Nullable identity operands and either period's partial/unavailable retained history suppress changes. Partial group counts are retained observations, not certified per-group lower bounds. Generation time is not a new receipt fence. Geography source/build/license provenance stays in each corresponding full report and applies to the same filtered population.

New selection/dimension reads take the existing workspace publication SHARE gate before the aggregation; the raw database clock, membership, API scope, revocation and expiry checks run after a real gate wait. SQL and lock deadlines are five seconds. The complete response with either new parameter is bounded to2MiB UTF-8; an oversized result fails503 rather than silently truncating the snapshot. There is no new storage, identity collection, provider request, export endpoint or report engine.

## Compare screen and applied URLs

The native Compare screen defaults to Path and offers the18 implemented dimension choices. Previous appears on the physical left and Current on the right, with the same selected dimension and each period's own dates, retained category count and at most20 rows. Current changes use the supplied full counterpart before either top20 cutoff; no aggregate category percentage is shown. These paired lists have no new search, More or CSV feature. Existing Geography and Environment detail flows retain their separate contracts.

`analyticsDimension` is Compare-only. `analyticsSelection` holds a bounded nested exact/presence query on Overview or Compare. The existing typed navigation validates its scalar shape; the panel validates the closed nine-field Match All contract before making any analytics request. Report-filter drafts do not alter the applied URL before Apply. Clicking either period's row applies its exact value or missing condition to the whole report; a geography child supplies compatible ancestors atomically. Empty strings, missing values and literal `not-recorded` strings remain distinct. Values remain text and cannot execute recorded URLs.

Same-project Overview/Compare links preserve applied dates and selection/environment/geography filters. Entering Overview removes comparison mode and dimension; returning without an explicit dimension defaults to Path. Unrelated views or new scopes drop analytics intent. Removing one filter family preserves the others. Malformed pairs and failed reads clear the displayed snapshot; stale project/account/request generations cannot republish it. The dimension DTO is validated against both parent periods, coverage and canonical selection before publication.

This is18 of the pinned reference's20 comparison choices. Distinct ID and Tag remain unimplemented; the recorded-channel method is still not the full upstream classifier. This increment adds no title, query string, tag or distinct-ID collection. Other required property comparisons and date presets remain open; no full reference parity is claimed.

## Runnable comparison UI checks

The existing optional `tests/analytics-comparison-browser.mjs` runner retains its original eight behavior groups and adds three groups when `TEN98_DIMENSION_SQL_SNAPSHOTS` points to an approved synthetic production-response capture. The actual-SQL groups consume complete captured reports without changing counts, scope or dates; extracted dimension-only objects are not fabricated into parent snapshots. Negative DTO copies and synthetic fallback cases are labelled separately. Run with `TEN98_COMPARISON_BROWSER=1` and the existing Playwright module/channel configuration. Browser execution requires an owned loopback server and is separate from server authorization acceptance.

`node --test tests/analytics-comparison.test.ts` checks strict selection, current-range compatibility, UTC previous-period boundaries, inclusive leap-day clamping, 367-day baselines, overlap and the 1970 lower bound. `tests/analytics-comparison-integration.ts` requires a fresh synthetic loopback PostgreSQL fixture on port 55501, the `ten98_comparison_<12 hex>` database prefix and both integration flags. It includes the complete existing analytics API assertions and exercises full-period metrics, both collection bases, filters, identity/zero denominators, independent retained-data gaps, calendar states, Viewer/tenant/cookie/key access, final key expiry and single-statement aggregation. Existing environment and retention integration checks must also pass without changing their expected behavior. Credentials and operational fixture scripts stay outside tracked code documentation.
