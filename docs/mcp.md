# Native MCP

This increment exposes 19 implemented native tools at `POST /api/mcp`. It uses the pinned official server/core SDK 2.3.1, modern protocol 2026-07-28 and the SDK's stateless legacy Streamable HTTP support. It is an incomplete P06 inventory: full pinned Elmo/OpenSEO tools, interactive OAuth authorization and paid-operation tools remain required work. It does not claim V1 completion or compatibility with an untested desktop client. See [native API](native-api.md) for the corresponding native contracts and [third-party notices](../THIRD_PARTY_NOTICES.md) for the SDK and bundled licenses.

Use one `Authorization: Bearer t98k_…` header. These are native workspace API keys, not OAuth tokens. Cookie authentication, cookies combined with a bearer, alternate `x-api-key`, and URL query parameters are refused. No authorization-server metadata, registration or automatic browser sign-in is advertised. A present `Origin` must exactly equal configured `APP_URL`, including scheme and port; absent Origin is allowed. Empty, `null`, multiple or nonmatching origins are refused. There is no wildcard CORS. GET, DELETE and OPTIONS return 405.

Each request creates its own official SDK server and handler. Modern requests use the official `_meta` envelope and matching `MCP-Protocol-Version`, `Mcp-Method` and, when required, `Mcp-Name` headers. The SDK owns protocol classification, metadata validation and finite JSON/SSE encoding. Legacy initialize and subsequent calls are stateless: there is no session ID or standalone GET stream. Modern responses use automatic JSON/SSE selection; finite legacy SSE remains supported. No tasks, resources, protocol prompts, sampling, roots, elicitation or subscriptions are advertised. Tool list-change notifications are disabled and the subscription limit is zero. SDK instances and the adapter's abort listener are closed/removed after completion, failure or cancellation; no second HTTP listener is created.

Discovery filters this fixed catalog by the key's current role-intersected grants. Write does not imply read. Each invocation independently reauthorizes; explicit project IDs must belong to the key's workspace. Native readers keep their SQL authority checks. Read results, discovery and whoami additionally pass a fresh publication decision; if effective authority changes while the response is prepared, the stale response is refused. This cannot retract bytes already delivered by an earlier request. No principal or tool list is cached between requests.

The endpoint reuses the existing 120 requests/key/minute budget. Realtime also uses 60/user/minute and the three session tools share 30/user/minute, including their native HTTP routes. Prompt transactions retain their workspace lock, current issuer/role check and final key check before commit. Expired writes roll back. Per-statement and lock-wait bounds are not a total-request timeout.

Journeys, Retention and Attribution each share their existing native HTTP 30/user/minute limit. Each receives the original API-key token, retains its native workspace admission and fresh SQL authority checks, and passes the existing MCP final publication checks. Inputs are strict native URL-wire objects without grouping, paging or arbitrary routing. Journeys permits optional dates/timezone and atomic typed start/end pairs with 2–7 steps (default 3). Attribution requires a typed conversion and defaults to first-click. Retention requires an explicit month and named timezone, and returns its native same-snapshot CSV. Each tool preserves null/zero, coverage, provenance and observed-key limitations; see [Journeys](journeys.md), [Retention](retention-report.md) and [Attribution](attribution.md). Separate tool calls are not one common snapshot. The existing 8 MiB complete MCP envelope, including both result copies, can refuse a native Journeys response below that reader's own 12 MiB ceiling; no successful prefix is returned.

The three context tools share the native `project-content` limit of 120 requests/user/minute with the cookie context routes and the prompt HTTP routes, in addition to the 120/key budget. They reuse the same `withContentProject` seam as the bearer prompt calls: READ COMMITTED, the workspace SHARE lock for reads or UPDATE lock for the write, five-second statement and lock-wait bounds, and the key's current authority checked after lock admission, again before publication or commit, and on the error path, so a stale key receives an authority refusal rather than the operation's own 404/409/503. The tool scope must equal the service scope; a mismatch fails closed with 403. `ten98_update_context` closes its top level and its eleven operation kinds; each operation's fields are validated once by the strict native context parser. None of the three makes a provider, DNS or Google call. The remaining content families (saved filters and cohorts, annotations, rank readers, saved keywords) land in the next slices; their scopes exist but admit no tool yet.

## Input and result contracts

Tools take strict named objects. Every project tool requires `projectId`; prompt detail/mutations use `promptId`, observed activity uses `visitorKey`. Read `query` objects contain native URL wire strings, not arbitrary URLs or routes. Session dates and named timezone are explicit; `pageSize` is a canonical string from `1` to `100`, and cursor scope is validated natively. Advanced `predicates` and `propertyValue` are JSON text interpreted by the existing bounded parsers. Native date, Unicode, geography composite-key, filter, cohort and cursor validation remains authoritative. Unknown argument/query fields reject the operation. Realtime accepts only projectId. Overview carries the accepted comparison and 500-row expanded location search; it does not create an unbounded export or cross-tool snapshot.

Every HTTP body is limited to 262144 actual UTF-8 bytes and decoded fatally by native `readJson` before the SDK receives `parsedBody`. Declared excess, invalid UTF-8/JSON and non-JSON content types are refused. JSON-RPC arrays/scalars are rejected. Request IDs are safe integers or strings of at most 128 UTF-16 code units. Prompt bulk is one atomic tool call of 1–100 entries, not JSON-RPC batching or an arbitrary operation dispatcher.

Successful reads return native DTOs in both `structuredContent` and JSON text content. Dates serialize to ISO strings; null, zero, retained coverage, identity limitations and provenance are preserved. Estimates describe rotating native keys, not persistent people. Each read has its own native snapshot semantics. Retention applies its raw receipt-time `asOf` cutoff to entry, qualification and return events. Journeys and Attribution retain their documented report clocks and calendar boundaries; their `asOf` is not an event-time fence. Complete HTTP responses, including duplicated result data and finite legacy framing, are capped at 8 MiB. Oversized reads return an error asking for a narrower selection, never a successful prefix. This response cap does not bound all database intermediate work.

The four prompt mutations and the context update return a compact receipt:

```json
{"committed":true,"requestId":"<submitted UUID>","replayed":false,"items":[{"id":"<prompt UUID>","revision":1,"currentVersionId":"<version UUID>","archivedAt":null}]}
```

```json
{"committed":true,"requestId":"<submitted UUID>","replayed":false,"revision":2}
```

The context receipt carries only the context revision after the batch; an identical retry returns the current revision with `replayed:true`, a changed payload under the same request ID or a stale revision conflicts, and no section, competitor, key page or research text is echoed. The prompt result is at most 100 fixed-shape identifiers/revisions/timestamps, below 64 KiB including both result copies at the tested maximum. Authored text, tags and classification are not repeated after commit. Native receipt replay returns the current state of the saved IDs, not an immutable historic snapshot. Reuse the same requestId only for the identical normalized operation; changed payload/operation conflicts. A transport interruption is not proof of rollback: retry that same requestId to resolve the outcome. Saving, enabling, editing, archiving and restoring never schedule or execute provider work. Write annotations are conservatively destructive and idempotent only under this explicit receipt contract.

Native tool failures use bounded `isError` results with safe status/message fields; protocol and ingress failures use JSON-RPC errors with appropriate HTTP status. Internal SQL, credentials, raw network values and stack traces are not returned. Unknown tool names cannot select arbitrary native functions; a catalog entry without its own dispatch case is a 500, never another tool's write. No tools accept code, SQL, provider endpoints or arbitrary request routing. Discovery performs no provider/catalog/network lookup, and this entire catalog makes no paid calls. The context neighbours `/ai-suggestions` (paid OpenRouter quote) and `/prompt-executions`, the rank catalog/locations/quote flows, saved-keyword refreshes, Google snapshots, site audits and the domains registry have no tool and stay cookie-only.

## Verification boundary

`tests/mcp.test.ts` checks the fixed schemas/scopes, complete UTF-8 size accounting, bounded receipts, exact Origin, and actual official modern/legacy catalog encoding; it also reads `src/server/mcp-tools.ts` to assert an explicit dispatch case for every catalog tool and a throwing default, and that the context update's kind enum is derived from the native `contextOp` union rather than copied. `tests/mcp-report-tools.test.ts` adds the three report schemas, unchanged native wire interpretation, closed scope/parameter boundaries and read-only SDK discovery. These pure checks do not establish database or transport acceptance. `tests/mcp-integration.ts` is opt-in and restricted to a fresh synthetic PostgreSQL fixture on `127.0.0.1:55501` (or the workflow's isolated `ten98_mcp_ci` database) with owned HTTP port 3111; it writes its report-tool evidence to the file named by `TEN98_MCP_REPORT_SNAPSHOTS`, which the workflow points into `ARTIFACT_DIR`. Its six original groups exercise the original 13 tools through native HTTP → handleApi → SDK → domain functions, transaction waits, late authority loss, receipts and provider inactivity. Four additive groups compare the three report tools with their actual direct readers and native HTTP routes over both MCP transports, including typed filters, cohorts, calendar boundaries, all four roles, 12 observed late-authority waits, complete-result refusals and shared native rate limits. Per-call report clocks are checked separately rather than treated as one common snapshot. One additive context group drives the three context tools through both transports: scope-filtered discovery for a `context:read` and a `context:write` key; `ten98_read_context` and `ten98_list_context_research` equal to the direct readers (`getProjectContext`, `getContextResearch` under the same key) and to the bearer HTTP route byte for byte on the modern and legacy transports; `ten98_update_context` returning the bounded receipt (`committed`, `requestId`, `replayed`, `revision`) with no authored text echoed and one receipt row, an identical retry and the native bearer POST replaying `replayed:true` at the same revision without a second receipt, 409 for a changed payload under the same request ID and for a stale revision, and two concurrent identical calls committing once; write-not-read refusals in both directions (and a report-only key refused on all three) over MCP and as HTTP 403; a foreign project answered 404 without leaking its ID; two observed revocation waits (one read, one write) that block on the workspace `FOR UPDATE` lock, lose the key while waiting and end 401 with no receipt and an unchanged revision; and the shared `project-content` rate key returning 429 on the tools and the cookie-shaped HTTP routes alike. The bearer HTTP CAS group in `tests/project-context-integration.ts` and the `/context` reader in `tests/api-key-delayed-reads-integration.ts` remain the route-level pins. The raw HTTP fixture uses `agent:false`; it does not establish official-client pooling compatibility. Production compilation is a separate check from actual compiled HTTP and resource acceptance.
