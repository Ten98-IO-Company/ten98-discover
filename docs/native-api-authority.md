# Native API read authority

Bearer reads of workspace projects/team and project recent events/Explorer recheck the existing API-key authorization after completing their data work and before creating the JSON response. The fresh statement checks expiry, revocation, current issuer membership/role, workspace and the route's required scope. The events reader waits on the workspace publication gate in a transaction of its own and releases it before reading, so a revocation or membership write during the read commits and the final check refuses the response; a failed Explorer report under a bearer runs the same fresh check before its own error is published. Explorer's final check runs outside its report transaction, so an older report snapshot cannot preserve a revoked key's authority.

This is a response-publication decision point. It cannot retract bytes already delivered. Browser-session behavior, response shapes, report calculations, saved retention boundaries and the stronger SQL authority checks in Analytics, Realtime and Sessions are unchanged. That increment exposed no new scopes or routes; the later content bearer routes (project context first) instead recheck authority inside `withContentProject` before commit and again after a rollback, the transaction-time variant of this publication rule.

`tests/api-key-delayed-reads-integration.ts` requires Node 24, both `TEN98_INTEGRATION_TEST=1` and `TEN98_API_KEY_DELAYED_READ_TEST=1`, and an already migrated empty synthetic database named `ten98_key_reads_<12hex>` on `127.0.0.1:55501` (or the workflow's isolated `ten98_key_reads_ci` database, migrated first). It owns loopback HTTP port3111 and requires `APP_URL=http://127.0.0.1:3111`. Supply isolated generated secrets; never use a customer database. Run `node tests/api-key-delayed-reads-integration.ts` with those fixture variables. A supervising runner must create/check the absent database, apply migrations, block non-fixture outbound traffic and verify cleanup.

The check uses real Node HTTP → `handleApi`, observed PostgreSQL lock waits and supported key/team mutations. It covers the four original readers under expiry/revocation/demotion/removal, valid bearer/browser data, scope/tenant/credential boundaries, the existing stronger readers and the context and segments readers. Demotion to Viewer preserves project/analytics read access while removing team access. It also invokes the original API-key integration checks without changing their oracles. No provider work is started.
