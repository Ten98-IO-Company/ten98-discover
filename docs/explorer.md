# Analytics exploration

> Code and safety contracts retained from [docs/explorer.md at dcd1b3d](https://github.com/Ten98-IO-Company/ten98-monitor/blob/dcd1b3de5f7e0600c6b459e6b20f08b072106097/docs/explorer.md). Historical/planning checkpoints: [implementation archive](https://wiki.ten98.io/s/ten98-docs/p/analytics-exploration-implementation-history-XhvZ0te4GU). Qualifications are preserved; this adds no acceptance claim.

Choose a project and **Explore**. Select inclusive calendar dates, a named timezone, event type and breakdown. More filters supports exact event/page/referrer/language/campaign matches and one typed property equality or missing-value condition. A saved result keeps its applied filters while you edit the next query; a visible notice identifies unapplied changes, and Apply filters executes the new query. Numeric summaries omit trailing decimal zeros for readability; CSV keeps the original exact decimal strings. All current members can read, and existing `analytics:read` API keys can use GET `/api/projects/:id/explore` within their workspace.

Advanced filters add ordered field conditions with an explicit all/any choice and typed event-property conditions that always require all matches. Existing exact filters stay required. The same controls support fixed cohort qualification without changing the report's own filters or dates.

**Origin** groups and exactly filters the authorized page origin, including verified serving domains. Use its serialized scheme and hostname (and a port only when the canonical project origin has one), without a trailing slash. Historical rows written before origin provenance was introduced belong to the immutable canonical project origin: the earlier collector permitted that origin only. Revoking a serving domain stops new collection but does not relabel its retained history. Origin does not create a separate visitor identity or a cross-domain person identifier; the existing project-scoped measurement rules still apply.

The overview remains UTC. Explore resolves named timezones using runtime and PostgreSQL timezone data, with1–366 local dates per request. Its UTC start/end are an inclusive/exclusive envelope, with an additional exact local-date predicate. Repeated midnight and historical dates that briefly reverse cannot be represented as a single ordinary calendar interval: adjacent envelopes may overlap, but the date predicate assigns each event to its actual local date. Missing midnight starts at the first real instant; a skipped date is labelled explicitly. Counts, daily buckets, breakdowns, property inventory and CSV share one database snapshot and filter population.

Properties use their exact normalized stored key, including escaped dots/backslashes and meaningful whitespace. Numeric42, string"42", empty string, null, missing, booleans, UTC dates and whole arrays remain separate. Numeric statistics use PostgreSQL decimal aggregation and return decimal text without conversion through JavaScript floating-point sums. Inventory and breakdown each return at most100 entries with explicit truncation; groups sort by event count then a stable label. Referrer absence is missing/uncollected, never assumed direct traffic.

Visitor/visit estimates cover only identified events and follow the existing rotating native identity contract. No valid identity means unavailable estimates, even when event counts are known. Retention is applied before every aggregate: expired ranges display unavailable counts, partial ranges contain only retained observations, and a genuinely empty available range is zero. The query has a five-second database deadline and a per-user rate limit; a deadline asks for narrower filters rather than silently returning a partial result. Raw aggregation has no production-volume guarantee.

**Download CSV** exports the exact currently displayed result, including applied scope, timezone, UTC envelope, retention status, totals, bounded groups, daily data and numeric statistics. Cells are quoted and leading spreadsheet formulas are neutralized. It is a bounded exploration export, not the complete seven-dataset ZIP/reset lifecycle required by P46. Loading, failed requests, access loss and project/account changes clear downloadable data. Saved funnels and goals are implemented; see [conversions](conversions.md). Paths, realtime/comparisons, replay and remaining V1 reports are still required.

## Saved filter contract

Saved Explorer filters are project-owned predicates, separate from applied report results. `parseSegmentDefinition` validates `{schemaVersion: 1, name, query}`: a trimmed nonblank name of at most 200 UTF-16 code units, matching the browser input, and a canonical query string of at most 20,000 characters. `explorerQuery` supplies the existing validation and normalization. The query includes `kind`, the exact Explorer filters and an optional typed property predicate; dates, timezone, grouping, cursors and unknown or repeated keys are rejected. Explicit empty values remain distinct from absent filters. Schema 0033 adds one `analytics_segment` table; no result cache or membership population is stored.

The browser-session API uses `/api/projects/:projectId/segments`:

| Method and suffix | Input | Result |
| --- | --- | --- |
| `GET /` | Optional single `cursor` | `{role, items, nextCursor}`, at most 50 items |
| `GET /:id` | No query parameters | `{role, item}` |
| `POST /` | `{requestId, definition}` | `{role, item, deleted, replayed}` |
| `POST /:id/update` | `{requestId, revision, definition}` | Same save envelope |
| `POST /:id/delete` | `{requestId, revision}` | `{role, id, deleted: true, replayed}` |

An item contains `id`, `projectId`, `revision`, `definition`, `createdAt` and `updatedAt`. All current members can read; owners, admins and editors can mutate. Writes use the existing workspace lock and recheck membership before applying changes or replaying receipts. Request identity binds the actor, operation and normalized payload. Replays return the current item, or `item: null, deleted: true` when it was deleted; they never recreate it. Updates and deletion require the loaded revision. Receipts retain identifiers only. The routes enforce configured Origin, no-store responses, bounded JSON, rate limits and scoped cursors; this adds no bearer-key permissions.

Loading a saved filter replaces the Explorer draft predicate and preserves its dates, timezone and grouping. It does not fetch analytics. Saving also leaves the currently applied result and CSV unchanged. Only Apply requests a new result. An uncertain write retains its exact request ID and payload for deliberate retry; a confirmed conflict requires a fresh read. Access loss clears protected display and cancels obsolete reads, while an unresolved write remains gated until current access is verified, including when another report controller discovers the denial. Account/project changes discard the old controller. These definitions do not represent cohorts, timeline annotations, session-property conditions, or automatic application to reports with different query semantics.

## Timeline notes

Schema 0034 stores project-owned `analytics_annotation` records, separate from events and saved filters. A note has a UTC millisecond instant, `allDay`, trimmed inert text of 1–500 UTF-16 code units, a revision and timestamps. `allDay` hides the time; it does not turn the instant into a floating date. Text-only edits preserve the saved instant and mode. Notes may be in the future, and analytics retention does not delete them or imply that traffic observations exist.

The session API at `/api/projects/:projectId/annotations` follows the saved-filter collection/detail/update/delete receipt and role envelopes above. Definitions accept `{date, allDay, note}`, where `date` is an explicit UTC/offset timestamp with at most millisecond precision, or `{day, timeZone, allDay: true, note}` for local calendar entry. These shapes cannot be mixed. Local dates resolve under the same calendar policy as Explorer: earliest repeated midnight, first real instant for a missing midnight, and rejection of a completely skipped date. Instants must fall within UTC years 1970–9998. Unknown offsets (`-00:00`) are rejected.

Collection reads accept optional paired `from`/`to` dates, `timeZone`, literal case-insensitive `search` and a scoped `cursor`. With no range they list all notes, including future ones. Pages contain at most 50 items, ordered by instant and ID; pagination is a live list. `GET /timeline?from=…&to=…&timeZone=…` returns `{role, range, days, totalCount}` for 1–366 local dates, where each nonempty day has an exact `count` and at most three item previews. The paged list provides full access beyond those previews. Query deadlines fail explicitly rather than silently truncating totals.

All current project members can read; owners, admins and editors can write. Mutation bodies are limited to 8 KiB. The existing transaction checks membership after workspace-lock admission, which has the pool's 10-second statement deadline; note queries have a 5-second deadline. Actor-bound receipts, revision checks and current-row/deleted-null replay prevent duplicate or resurrected notes. This adds no API-key scope or provider request.

Overview and Explorer share one note controller per account/project. Day counts open the matching notes; the manager supports the applied date range, all notes, literal search and pagination. The default date uses the applied report's end date and timezone (UTC in Overview), not unapplied form changes. Notes remain readable when traffic is empty or outside retention. Note operations do not request analytics or alter the applied CSV. Unknown mutations retain their exact request across range changes; access loss purges displayed text and gates retry until current access is verified. Account/project changes discard obsolete responses.

## Saved observed-visitor cohorts

Schema 0035 stores project-owned `analytics_cohort` definitions, not materialized membership. `parseCohortDefinition` accepts `{schemaVersion: 1, name, query}` with the saved-filter name/size boundaries. The canonical qualification query requires explicit `from`, `to` and `timeZone`, and exactly one `path` or `eventName` key; an empty exact value remains distinct from absence. It preserves the supplied event kind and supported exact/typed predicates. Dates span 1–366 local days and cannot end after today in the selected timezone. Grouping, cursors, repeated keys and nested cohort references are rejected. The session collection/detail/update/delete routes at `/api/projects/:projectId/cohorts` use the same role, revision and receipt envelopes as saved filters.

Explorer accepts a paired `cohortId` and `cohortRevision`. It reads the authorized saved definition and executes qualification/report queries in one repeatable-read snapshot. A stale revision returns 409; unavailable or foreign definitions return 404. Distinct non-null visitor keys from retained qualifying events restrict report activity through a semijoin, so repeated qualifying events cannot duplicate report totals. Qualification dates and report dates are separate. Both use the existing calendar and predicate SQL; funnels do not accept this cohort scope.

The optional `cohort` response contains the applied item/revision, resolved qualification range, its retention coverage, identified/unidentified qualifying-event counts, observed member-key count, membership status and limitations. Expired qualification history or qualifying events with no identifiers make membership unavailable: report totals/daily values and group summary counts are null, groups/property keys are empty, and numeric statistics are null. Partially retained qualification or some unidentified qualifiers produces observed lower bounds. A fully retained qualification with genuinely no events yields an empty observed set. Report retention remains a separate field, and the returned CSV includes the applied qualification metadata in the same snapshot.

Visitor keys are project-scoped and rotate each UTC month and when identity inputs or the signing secret change. They are not persistent people or a basis for linking activity across those changes. Identity coverage describes only retained qualifying events. This increment supports fixed-date Explorer membership; it does not implement rolling cohort ranges, session-property membership or the separate retention report.

In the interface, selecting/loading a cohort stages its verified ID and revision; only Apply changes the report. The qualification editor has independent dates and predicates. Saving, loading, clearing or deleting a cohort leaves the last successful result/CSV intact. A stale or deleted reference cannot silently broaden the report: users must explicitly clear it or load a current definition before applying. Current-role checks, immutable uncertain-write retries and account/project response isolation cover the cohort controller as well as the existing saved-filter and note controls.

## Advanced event and dimension predicates

The optional single `predicates` query parameter contains `{version: 1, match: "all" | "any", fields: [...], properties: [...]}`. Each field has `field`, `operator` and, when needed, `value`; each property has `key`, `operator`, and the required `type`/`value`. The strict parser rejects unknown members, nested groups, unsupported dimensions and repeated URL parameters. It permits at most 20 additional conditions, including at most 10 properties, and requires at least one. `any` requires a nonempty field group. Ordered repeated clauses, literal whitespace and commas are preserved. The complete canonical advanced report query, including resolved defaults, is limited to 20,000 URL-encoded characters.

The population is the existing authorized calendar/retention/kind scope **AND** every existing exact filter/property **AND** the additional field group **AND** every additional property condition. Cohort qualification also requires its original action on that same event row. Saved filters and cohort definitions preserve the versioned object; old definitions retain their canonical bytes and meaning. Report and qualification responses/CSV include separate `predicateMethod` metadata describing the applied groups, text/regex policy and timezone date comparison. Funnels retain their original strict scope and operators.

| Target | Operators |
| --- | --- |
| Collected string dimensions and typed string event properties | `eq`, `neq`, `contains`, `not_contains`, `prefix`, `suffix`, `regex`, `not_regex` |
| Typed number properties | `eq`, `neq`, `gt`, `gte`, `lt`, `lte` |
| Typed boolean and null properties | `eq`, `neq` |
| Typed date properties | `eq`, `neq`, `before`, `after` |
| Typed arrays | Ordered whole-array `eq`/`neq`, scalar typed `includes`/`not_includes` |
| Dimensions or any property key | `exists`, `missing`, with no operand or property type |

Equality is case-sensitive. Text contains/prefix/suffix uses PostgreSQL lowercasing and literal matching; `%`, `_` and backslash are not wildcards. Regex uses PostgreSQL's case-insensitive engine and is validated even for empty datasets or saved definitions. Invalid syntax returns a generic 400; database cancellation returns 503 under the existing five-second statement deadline. Save validation runs after current authorization and receipt replay; an exact replay cannot overwrite later data. Unknown save outcomes retain the original request for deliberate confirmation.

Typed negatives require a collected value of the declared type; missing is separate from null or an empty value. Date equality retains normalized fractional precision. Before/after excludes the selected calendar day in the report or qualification timezone; subsecond precision is discarded only for calendar conversion, preventing rounding across midnight. Native year-zero dates remain before every permitted comparison day. Fixed SQL maps and bound operands preserve the existing report/qualification parameter slots; all report aggregates use one filtered population in the same snapshot.

The interface shows required filters, additional all/any fields and property conditions as separate groups. Adding, removing and loading rows remains draft-only; incomplete rows block Apply/Save instead of being silently omitted. Removing the last field explicitly leaves any property conditions required. These controls cover collected dimensions and event properties. [Native identify](analytics-measurement.md#native-identify-and-session-properties) stores session properties separately; session-property conditions, uncollected source dimensions and the remaining full P35 reports remain required work.

## Model and source evidence

The design follows Umami's focused filtering/breakdown pattern and the stored native property contract. PostgreSQL calendar operations are based on its [date/time documentation](https://www.postgresql.org/docs/18/functions-datetime.html); regression fixtures determine edge behaviour. This slice copies no upstream application source.
