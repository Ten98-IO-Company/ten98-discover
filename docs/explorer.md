# Analytics exploration

## Event property details

`GET /api/projects/:id/explore?...&groupBy=property&groupProperty=<exact-key>&propertyView=details` adds `propertyReport`; requests without that flag keep their existing scalar/tuple response. The mode is report-only and cannot enter saved segment/cohort definitions. The interface enables **Property analysis and event properties** after choosing a property, then reuses Apply/Refresh, applied-snapshot CSV, current access purge and draft indicators. Tabs show typed value series, exact daily numeric statistics, property date values, array-element occurrences and matching event properties. No model/provider request is involved.

Value and array series use the existing local event-day calendar and complete filtered population, including advanced filters, current retained session-property conditions and cohorts. Numeric sums/averages remain decimal strings; days without numeric samples have zero samples and unavailable aggregates. Missing, null, empty strings, numbers and strings stay distinct. Array elements preserve their primitive types and repeated elements count repeatedly; an empty array contributes an array sample but no element occurrences. Date distribution uses the actual normalized UTC property value, independently of the event's receipt day. These distinctions follow the pinned Umami property/numeric/date/array flows while retaining native typed identities.

Each value/array/date inventory returns at most100 entries with explicit total/truncation metadata; series counts come from all matching observations, not a client-side pivot of the displayed groups. Event rows include anonymous observations and their normalized typed properties. Pages contain50 rows ordered by exact microsecond receipt time and UUID. `propertyCursor` is a bounded canonical base64url record bound to project/query hash, original native statement-clock bound and current retention-policy hash; a changed scope is400 and changed policy is409. It grants no authority; every page repeats current project membership/analytics-key admission. The workspace SHARE gate and existing five-second SQL/250ms lock bound apply to this mode.

All sections and same-response CSV share a snapshot. Unavailable history/selection returns empty series/rows and null statistics, never fabricated zero; partial evidence is labelled. The whole new response including CSV is limited to2097152 UTF-8 bytes and fails503 completely when oversized. The UI reuses the bounded20-second JSON reader, fatal UTF-8 decoding and access-first error handling. CSV is formula-safe and covers the displayed event page, with a more-pages marker. No schema, dependency, cache or worker is added.

### Numeric and property-date visuals

Property analysis adds `numberStats` (samples, sum, average, median, minimum and maximum) and `dateSummary` inside `propertyReport`. The existing top-level `numeric` and absent-mode CSV retain their prior shape. The numeric chart compares signed daily sums and averages on one zero-centred scale. PostgreSQL numeric strings remain the source for labels, summaries and CSV; the median is the exact midpoint of the middle one/two ordered samples. PostgreSQL determines average division precision. Only chart coordinates round toward zero to one millionth of the shared scale using bounded BigInt arithmetic. Decimal text is limited to1024 characters before conversion; exponents, non-finite text and malformed metadata are refused. Tiny bars may be subpixel; the exact table remains available. No samples means zero samples and null statistics; unavailable evidence means null samples and statistics. Partial sums, averages, medians and extrema describe observed data and are not claimed as lower bounds.

The date histogram and summaries aggregate **all matching date observations before the exact-value table's100-entry limit**. Their calendar uses the applied report timezone and property date values, independently of event receipt dates. Span thresholds follow pinned Umami: up to45 calendar days uses days,46–180 uses weeks,181–730 uses months, otherwise years. Weeks explicitly start Monday, independently of browser locale. Calendar buckets between the observed earliest/latest values are zero-filled; unavailable history is not. Top-date ties choose the latest local date; top-weekday ties choose the first Monday-to-Sunday weekday. The interface shows top weekday/date, earliest/latest local date, histogram, weekday counts/shares, and the unchanged exact UTC frequency table. CSV includes timezone, Monday week convention, numeric median, full histogram and all weekday counts.

Native SVG rings and adjacent count/share tables show typed values, array occurrences and weekdays. Values divide by matching event count; arrays divide by all element occurrences, including repeated elements. Weekdays divide by all observed date samples. The first eight returned values have individual ring segments, with **Other returned values** and **Values omitted from the exact table** kept separate when their exact residual counts are known. Typed labels remain distinct, colours are deterministic from typed identity, and patterned residual segments have matching legend swatches. Shares always describe the observed population, including under partial retention. Unavailable denominators produce no ring or invented zero. CSV preserves each returned count and its exact denominator; percentages in the interface are display-rounded to one decimal place.

Native year0000 maps to PostgreSQL1BC only for calendar conversion. Timezone boundary dates may therefore use ISO extended labels `-000001` or `+010000`; exact input UTC strings are preserved. Fractional seconds are discarded for calendar conversion without rounding into the next day. Malformed stored date values fail the complete report. At most10002 histogram buckets are accepted by the reader, covering the native four-digit UTC year range and timezone boundary years, under the unchanged whole-response size/deadline limits.

Reference: pinned Umami `ec0ff50388c264ed8ce46f00967e92f7e71476ae`, `PropertyDateChart`, `PropertyNumericChart`, `PropertyChart` and their PostgreSQL query implementations. Native SVG charts and the exact tables implement the date/numeric analysis flow without a chart dependency. Fixed Monday weeks, explicit unknown/retention semantics and the native typed-value table differ from upstream locale and zero-coalescing behavior; this is not a claim of complete visual1:1 parity. Source-only authored checks cover bucket thresholds, more than100 date values, timezone/year edges, exact signed medians, invalid metadata and narrow LTR/RTL CSS-zoom layouts; execution is a separate acceptance step.

Source is authored; pure/native/browser/type/resource acceptance and final visual parity remain pending. New checks are additive to the original scalar/compound oracles. This is not a production-readiness claim.

## Compound grouping increment

The existing Explore screen offers **Single field** and **Combined fields**. The breakdown path accepts one to three different scalar fields; a single-field breakdown returns the same page-view metrics as multi-field breakdowns. The legacy Single field event/property wire contract is unchanged. The source × medium × campaign preset stages those fields and **Page views**; review the draft scope and select **Apply filters**. Editing selectors, reordering fields or loading saved predicates does not change the accepted result or its CSV. Refresh and unchanged Apply each request a fresh report. Grouping is local to this screen: it is not saved in segment/cohort definitions or the page URL.

`GET /api/projects/:id/explore?fields=["campaignSource","campaignMedium","campaignName"]` uses a JSON-encoded array on the wire; users select ordinary labelled fields. `fields` is mutually exclusive with `groupBy` and `groupProperty`, excludes property grouping, and rejects duplicates/unknown fields. Both raw and normalized encoded queries retain the20,000-character bound. Other reports continue using the unchanged scalar Explorer parser. No request without `fields` gains new response keys.

Compound `query` echoes ordered `fields` instead of scalar grouping keys. Each breakdown row has `type:"tuple"` and `value:[{type,value},…]`, followed by the existing `events`, `identifiedEvents` and nullable `visitors` (all matching events). It additionally returns `pageViews`, `identifiedPageViews`, nullable `estimatedVisitors` and `visits` (matching page views only), `bounceRate` (percent) and `averageVisitSeconds`. Missing evidence, empty strings, literal sentinel-like text, numeric screen dimensions and country-qualified canonical geography keys remain distinct. Full matching observations are aggregated before the deterministic top500 limit, ordered by page-view estimated visitors descending (null last), page views descending, then the canonical tuple text under C collation. `totalGroups`, returned group events and truncation describe the complete versus returned population. Custom-only groups remain visible with zero page views and unavailable page-view key metrics. Unavailable history/selection produces null summary counts, not measured zero. Current retained-property/cohort/retention semantics and metadata remain unchanged.

The page-view calculation follows pinned Umami3.4 `getBreakdown`: each tuple/visitor/visit is one visit observation. Duration is its last minus first **matching page view**, in seconds; the average weights each visit once, including zero-second visits. One matching page view is a bounce only when that visitor/visit has no retained custom event anywhere in the authorized project and selected local dates, before exact, advanced, kind, session-property or cohort report filters. Another path's page view does not suppress the bounce. Both visitor and visit keys identify the pair; identical visit IDs under different visitors stay separate. Native keys rotate, so these are observed-key estimates, not persistent people or complete sessions. Anonymous page views stay counted but cannot establish key metrics. Mixed groups expose the observed keyed subset through `identifiedPageViews`; do not sum visitor/visit estimates across groups. Partial history or incomplete cohort/current-property selection retains observed counts and suppresses rates/duration.

This extends the pinned page-view report with existing all-event tuple groups and all-event visitor counts; it does not claim identical upstream output. Requests without `fields` retain their scalar DTO, CSV and top100 behavior. The remaining P36 field inventory, five-UTM flows and saved reports remain required. Metrics acceptance is pending: source-only assertions cover group spans, cross-filter custom suppression, equal visit IDs under different visitors, weighted durations, anonymous/partial evidence and complete501→500 ranking. Historical pre-metrics acceptance does not validate this increment.

The CSV is generated from that same accepted result and includes typed values per field, qualified geography plus canonical keys, scope and evidence metadata. Formula protection remains in the existing CSV helper. Complete compound JSON including CSV is capped at2MiB UTF-8; the server refuses an oversized whole response with503. The compound browser reader bounds decoded bytes, rejects malformed UTF-8/JSON/redirects/contradictory tuple DTOs and purges exports on errors or access loss.

This is the first P36 tuple-count vertical, not complete upstream parity. Pinned Umami3.4 `getBreakdown` groups an array of fields and exposes views/visitors/visits/bounce/time with up to500 rows; its `getUTM`/UTM screen provides five separate marginal campaign summaries. Visit/bounce/duration tuple metrics, broader selection/complete inventory, five marginal UTM summaries, persisted report intent and remaining P33/P36 requirements remain open. `ten98_list_segments` and `ten98_list_cohorts` read saved selections; no Explorer grouping tool is introduced.

Additive checks are authored in the existing pure, native integration and browser runners. The native pressure case intentionally uses adversarial strings accepted by the stored SQL schema; it does not claim those strings are normalized collected URLs. Browser contradictions are explicitly synthetic negative copies of actual responses. Body CSS zoom200% is not browser zoom. ## Saved filter contract

Saved Explorer filters are project-owned predicates, separate from applied report results. `parseSegmentDefinition` validates `{schemaVersion: 1, name, query}`: a trimmed nonblank name of at most 200 UTF-16 code units, matching the browser input, and a canonical query string of at most 20,000 characters. `explorerQuery` supplies the existing validation and normalization. The query includes `kind`, the exact Explorer filters and an optional typed property predicate; dates, timezone, grouping, cursors and unknown or repeated keys are rejected. Explicit empty values remain distinct from absent filters. Schema 0033 adds one `analytics_segment` table; no result cache or membership population is stored.

The browser-session API uses `/api/projects/:projectId/segments`:

| Method and suffix | Input | Result |
| --- | --- | --- |
| `GET /` | Optional single `cursor` | `{role, items, nextCursor}`, at most 50 items |
| `GET /:id` | No query parameters | `{role, item}` |
| `POST /` | `{requestId, definition}` | `{role, item, deleted, replayed}` |
| `POST /:id/update` | `{requestId, revision, definition}` | Same save envelope |
| `POST /:id/delete` | `{requestId, revision}` | `{role, id, deleted: true, replayed}` |

An item contains `id`, `projectId`, `revision`, `definition`, `createdAt` and `updatedAt`. All current members can read; owners, admins and editors can mutate. Writes use the existing workspace lock and recheck membership before applying changes or replaying receipts. Request identity binds the actor, operation and normalized payload. Replays return the current item, or `item: null, deleted: true` when it was deleted; they never recreate it. Updates and deletion require the loaded revision. Receipts retain identifiers only. The routes enforce configured Origin, no-store responses, bounded JSON, rate limits and scoped cursors; bearer and MCP reads of saved filters and cohorts require `segments:read` (see [native API](native-api.md)), while writes stay cookie-only.

Loading a saved filter replaces the Explorer draft predicate and preserves its dates, timezone and grouping. It does not fetch analytics. Saving also leaves the currently applied result and CSV unchanged. Only Apply requests a new result. An uncertain write retains its exact request ID and payload for deliberate retry; a confirmed conflict requires a fresh read. Access loss clears protected display and cancels obsolete reads, while an unresolved write remains gated until current access is verified, including when another report controller discovers the denial. Account/project changes discard the old controller. These definitions do not represent cohorts, timeline annotations or automatic application to reports with different query semantics.

## Timeline notes

Schema 0034 stores project-owned `analytics_annotation` records, separate from events and saved filters. A note has a UTC millisecond instant, `allDay`, trimmed inert text of 1–500 UTF-16 code units, a revision and timestamps. `allDay` hides the time; it does not turn the instant into a floating date. Text-only edits preserve the saved instant and mode. Notes may be in the future, and analytics retention does not delete them or imply that traffic observations exist.

The session API at `/api/projects/:projectId/annotations` follows the saved-filter collection/detail/update/delete receipt and role envelopes above. Definitions accept `{date, allDay, note}`, where `date` is an explicit UTC/offset timestamp with at most millisecond precision, or `{day, timeZone, allDay: true, note}` for local calendar entry. These shapes cannot be mixed. Local dates resolve under the same calendar policy as Explorer: earliest repeated midnight, first real instant for a missing midnight, and rejection of a completely skipped date. Instants must fall within UTC years 1970–9998. Unknown offsets (`-00:00`) are rejected.

Collection reads accept optional paired `from`/`to` dates, `timeZone`, literal case-insensitive `search` and a scoped `cursor`. With no range they list all notes, including future ones. Pages contain at most 50 items, ordered by instant and ID; pagination is a live list. `GET /timeline?from=…&to=…&timeZone=…` returns `{role, range, days, totalCount}` for 1–366 local dates, where each nonempty day has an exact `count` and at most three item previews. The paged list provides full access beyond those previews. Query deadlines fail explicitly rather than silently truncating totals.

All current project members can read; owners, admins and editors can write. Mutation bodies are limited to 8 KiB. The existing transaction checks membership after workspace-lock admission, which has the pool's 10-second statement deadline; note queries have a 5-second deadline. Actor-bound receipts, revision checks and current-row/deleted-null replay prevent duplicate or resurrected notes. `annotations:read` admits bearer and MCP reads of the list, timeline and single notes; writes add no key scope, and nothing here makes a provider request.

Overview and Explorer share one note controller per account/project. Day counts open the matching notes; the manager supports the applied date range, all notes, literal search and pagination. The default date uses the applied report's end date and timezone (UTC in Overview), not unapplied form changes. Notes remain readable when traffic is empty or outside retention. Note operations do not request analytics or alter the applied CSV. Unknown mutations retain their exact request across range changes; access loss purges displayed text and gates retry until current access is verified. Account/project changes discard obsolete responses.

## Saved observed-visitor cohorts

Schema 0035 stores project-owned `analytics_cohort` definitions, not materialized membership. `parseCohortDefinition` accepts `{schemaVersion: 1, name, query}` with the saved-filter name/size boundaries. The canonical qualification query requires explicit `from`, `to` and `timeZone`, and exactly one `path` or `eventName` key; an empty exact value remains distinct from absence. It preserves the supplied event kind and supported exact/typed predicates. Dates span 1–366 local days and cannot end after today in the selected timezone. Grouping, cursors, repeated keys and nested cohort references are rejected. The session collection/detail/update/delete routes at `/api/projects/:projectId/cohorts` use the same role, revision and receipt envelopes as saved filters.

Explorer accepts a paired `cohortId` and `cohortRevision`. Without session conditions, it reads the authorized saved definition and executes qualification/report queries in the existing repeatable-read snapshot. Session-aware reports use the gated transaction described below. A stale revision returns 409; unavailable or foreign definitions return 404. Distinct non-null visitor keys from retained qualifying events restrict report activity through a semijoin, so repeated qualifying events cannot duplicate report totals. Qualification dates and report dates are separate. Both use the existing calendar and predicate SQL; funnels do not accept this cohort scope.

The optional `cohort` response contains the applied item/revision, resolved qualification range, its retention coverage, identified/unidentified qualifying-event counts, observed member-key count, membership status and limitations. Expired qualification history or qualifying events with no identifiers make membership unavailable: report totals/daily values and group summary counts are null, groups/property keys are empty, and numeric statistics are null. Partially retained qualification or some unidentified qualifiers produces observed lower bounds. A fully retained qualification with genuinely no events yields an empty observed set. Report retention remains a separate field, and the returned CSV includes the applied qualification metadata in the same snapshot.

Visitor keys are project-scoped and rotate each UTC month and when identity inputs or the signing secret change. They are not persistent people or a basis for linking activity across those changes. Identity coverage describes only retained qualifying events. This supports fixed-date Explorer membership, including current session-property conditions; rolling cohort ranges and the separate retention report remain required.

In the interface, selecting/loading a cohort stages its verified ID and revision; only Apply changes the report. The qualification editor has independent dates and predicates. Saving, loading, clearing or deleting a cohort leaves the last successful result/CSV intact. A stale or deleted reference cannot silently broaden the report: users must explicitly clear it or load a current definition before applying. Current-role checks, immutable uncertain-write retries and account/project response isolation cover the cohort controller as well as the existing saved-filter and note controls.

## Advanced event and dimension predicates

The optional single `predicates` query parameter contains `{version: 1, match: "all" | "any", fields: [...], properties: [...]}`. Each field has `field`, `operator` and, when needed, `value`; each property has `key`, `operator`, and the required `type`/`value`. The strict parser rejects unknown members, nested groups, unsupported dimensions and repeated URL parameters. It permits at most 20 additional conditions, including at most 10 event and session property conditions combined, and requires at least one. `any` requires a nonempty field group. Ordered repeated clauses, literal whitespace and commas are preserved. The complete canonical advanced report query, including resolved defaults, is limited to 20,000 URL-encoded characters.

The population is the existing authorized calendar/retention/kind scope **AND** every existing exact filter/property **AND** the additional field group **AND** every additional property condition. Cohort qualification also requires its original action on that same event row. Saved filters and cohort definitions preserve the versioned object; old definitions retain their canonical bytes and meaning. Report and qualification responses/CSV include separate `predicateMethod` metadata describing the applied groups, text/regex policy and timezone date comparison. Funnels retain their original strict scope and operators.

| Target | Operators |
| --- | --- |
| Collected string dimensions and typed string event properties | `eq`, `neq`, `contains`, `not_contains`, `prefix`, `suffix`, `regex`, `not_regex` |
| Typed number properties | `eq`, `neq`, `gt`, `gte`, `lt`, `lte` |
| Typed boolean and null properties | `eq`, `neq` |
| Typed date properties | `eq`, `neq`, `before`, `after` |
| Typed arrays | Ordered whole-array `eq`/`neq`, scalar typed `includes`/`not_includes` |
| Dimensions or any property key | `exists`, `missing`, with no operand or property type |

Equality is case-sensitive. Text contains/prefix/suffix uses PostgreSQL lowercasing and literal matching; `%`, `_` and backslash are not wildcards. Regex uses PostgreSQL's case-insensitive engine and is validated even for empty datasets or saved definitions. Invalid syntax returns a generic 400; database cancellation returns 503 under the existing five-second statement deadline. Save validation runs after current authorization and receipt replay; an exact replay cannot overwrite later data. Unknown save outcomes retain the original request for deliberate confirmation.

Typed negatives require a collected value of the declared type; missing is separate from null or an empty value. Date equality retains normalized fractional precision. Before/after excludes the selected calendar day in the report or qualification timezone; subsecond precision is discarded only for calendar conversion, preventing rounding across midnight. Native year-zero dates remain before every permitted comparison day. Fixed SQL maps and bound operands preserve the existing report/qualification parameter slots; all report aggregates use one filtered population in the same snapshot.

The interface shows required filters, additional all/any fields and property conditions as separate groups. Adding, removing and loading rows remains draft-only; incomplete rows block Apply/Save instead of being silently omitted. Removing the last field explicitly leaves any property conditions required. These controls cover collected dimensions, event properties and current retained session properties. [Native identify](analytics-measurement.md#native-identify-and-session-properties) stores session properties separately. Uncollected source dimensions and the remaining full P35 reports remain required work.

## Current session-property conditions

Version 1 predicates accept optional ordered `sessionProperties`, using the same typed property rows and operators as `properties`. Absent and empty groups normalize to omission, preserving existing canonical definitions. All session conditions require all matches, independently of the field all/any choice. Each condition reads the latest retained value for the qualifying event's project-scoped rotating visitor key; event dates do not restrict property update dates. The qualifying action and event conditions still match one event. Later identify updates or expiry can change an explicitly rerun older report or cohort without changing its definition revision.

Unidentified events are excluded from every session condition, including `missing`. Typed negative operators require a retained value of the declared type. Missing means unobserved for an identified rotating key only while no property evidence loss is known. Sticky loss or a physically retained expired property makes any Missing selection unavailable, even with zero candidates or an unrelated expired key. Positive selections can report observed count lower bounds; that statement does not apply to sums, averages, extrema, rates or rankings.

Session-aware reads hold workspace SHARE with a 250ms admission timeout, then freshly authorize and resolve the selected cohort in READ COMMITTED. A session-bearing cohort discovered during legacy classification causes rollback and fresh resolution on the same connection; stale revisions return409 and deletion/current access loss404. Non-session reads keep the original repeatable-read behavior. One five-second data statement binds the snapshot clock, policy cutoff, profile evidence, pre-session identity candidates, qualification, report population and every aggregate; no profile metadata is written by a read.

Optional report `sessionProperties` and qualification `cohort.sessionProperties` metadata expose method, snapshot `asOf`, effective `retainedFrom`, sticky/pending evidence loss, identified/unidentified candidate counts, selection status/reason and count-bound flag. These are separate from event retention and ordinary cohort identity coverage. Missing evidence, wholly unidentified candidates or an unavailable candidate scope redact affected totals/daily counts, groups, property keys and numeric summaries. The exact returned CSV includes the same metadata. Empty session groups add no metadata to legacy responses.

The interface separates **Current session properties — all** from event properties in both report and qualification editors. Loading/saving remains staged; Apply executes a new report and Refresh reevaluates current properties. Invalid or missing metadata withholds replacement results/CSV instead of inventing zero. Saved filters preserve both property groups; old definitions clear session rows. Persistent-person continuity and historical property versions are not claimed.

## Model and source evidence

The design follows Umami's focused filtering/breakdown pattern and the stored native property contract. PostgreSQL calendar operations are based on its [date/time documentation](https://www.postgresql.org/docs/18/functions-datetime.html); regression fixtures determine edge behaviour. This slice copies no upstream application source.

Property event pagination excludes later arrivals using its original event-receipt bound. Every page rechecks current retention, saved-cohort authority and current session-property selection; eligible events and report counts can change between pages. This is not a cross-page database snapshot. A retention cursor conflict clears displayed data and export, preserves the draft/cohort, and Retry reloads the first event page.

## Returning to Analytics

The explicit Analytics navigation from Explore projects the applied URL, not filter-dialog drafts or comparison presentation. A complete UTC, All events scope carries the closed browser/OS/device and typed geography filters plus supported literal page, event, referrer, language, campaign, origin, recorded hostname, physical screen and recorded channel selections. Supported additional field conditions are all-match equality, recorded or missing, with one condition per supported field. Validated grouping and display choices do not restrict the population and are not carried.

Analytics currently cannot represent Explore cohorts, event or session property conditions, non-UTC calendars, pageview/custom-only kind, or other advanced operators. Any such applied condition blocks the entire Analytics request; no condition is silently removed. The invalid view explains this limit and offers an explicit reset that deliberately clears the scope. These missing Analytics capabilities remain required broader work.

The transition stores only an exact relative Explore return address in native router history state, bound to the current user/workspace/project. Its bounded complete scope and canonical wire representation are revalidated before Return to Explorer is offered. Reload retains valid history state. A copied link, malformed state or changed identity cannot recover that address and says so; no return metadata is accepted in URL parameters. This is not authorization or saved-report storage.

A default Explore URL has no explicit dates. Only a successful verified ready UTC default report supplies the existing account/project/history-entry-bound applied-range callback; return uses that remembered range rather than recalculating it after midnight. An explicit canonical query always takes precedence. Loading, unavailable, invalid or unsupported default states cannot publish a remembered range.

Controlled Analytics/Compare reads now use the same canonical router/validated-prop and history-entry ownership pattern as Explore. A mismatch blocks report and annotation reads and hides old results; late completions from an obsolete entry or identity cannot restore them. The note controller retains stable applied dates and immutable pending writes while read ownership changes. Existing note and saved-filter blockers still require deliberate confirmation before abandoning an uncertain write.

The focused source-fixture runner retains its original13 groups and adds6 reverse-return groups (19 total). Its success/error API bodies remain synthetic and do not establish native database or compiled acceptance. Two additive navigation unit groups cover the reused final wire boundary; direct scope projection/history validation cases run through the actual browser component exports. The default-date case uses the installed Playwright clock to simulate UTC midnight, not an advanced server clock.


Recorded hostname, physical screen and recorded channel are ordinary scalar groups and exact/advanced filters. They reuse the comparison projections. Hostname never substitutes the current project origin; missing physical screens remain missing. Channel is recorded-channel-tags-v1 rather than a full visit/referrer classifier; a referrer host equal to the host of the event's own recorded origin, port dropped and a leading www. ignored on both sides (a self-referral, D11), is not a referrer there, so in-app views of a direct visit stay `not_recorded`, while the referrer group itself still lists that host. Grouping edits remain staged; removing the last remaining breakdown field is unavailable. No collector, consent or retention changes accompany these readers.
