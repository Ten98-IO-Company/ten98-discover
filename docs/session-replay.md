# Session replay contract

Replay has a separate recorder, consent choice, retained-recording library and isolated player. Migration0055 follows the registered0053/0054 prefix. The browser asset is vendored without adding a Node dependency. Saved replays/heatmaps(P42) and boards(P43) are separate features; this contract does not imply their implementation or full application readiness.

## Permission and settings

Existing analytics settings may omit `replay`; omission means disabled. The optional closed object contains `enabled`, `sampleRate`0–1 (including0), `maskLevel`strict/moderate, `maxDurationMs`300000/600000/900000/1200000, and a block selector up to1024characters. Defaults are disabled,15%sampling, strict masking,5minutes, and no extra selector. A legacy settings form that omits replay preserves the saved replay setting. Settings saves rotate the existing combined native/destination consent epoch.

Replay requires current analytics collection enabled, replay enabled, configured exact website Origin/site key, the current combined epoch, and separate explicit `{analytics:true,replay:true,epoch}` consent. Analytics consent, an API key or cookieless policy alone never authorizes DOM capture. Existing path exclusions, publication locks, DNT/GPC, bot exclusion and the installation network-address exclusion (`ANALYTICS_EXCLUDED_IPS`) apply. A changed setting/epoch invalidates outstanding upload capabilities. This is a public-site permission envelope; the server cannot prove that an arbitrary public client actually displayed a consent notice or masked its DOM.

The recorder retains only its short-lived upload capability and recording position in per-tab `sessionStorage` after explicit replay consent, to continue a recording across ordinary same-origin navigation. No raw-DOM queue is persisted. Withdrawal, configuration expiry and excluded routes stop recording and discard pending DOM. Input/text masking and block selectors apply before transport. An interrupted upload reserves an explicit sequence gap rather than reusing its sequence or inventing a final receipt. A fresh acknowledged consent choice can start a new recording; it never replays earlier activity.

## Collection and immutable capability

`POST /api/replay/begin` accepts exactly `{siteKey,requestId,url,consent}`. URL must be HTTP(S), without credentials, query or fragment, with a bounded path. It returns accepted/not-sampled, recordingId, optional upload token, original created/deadline/upload-until instants, immutable settings and limits. A unique `(project,requestId)` and request hash resolve concurrent/lost-ACK retries. Sampling is persisted once; retries neither resample nor extend deadlines. Changing the request under that key conflicts.

The HMAC capability is domain-separated from analytics contexts and bound to project, recording, exact origin, combined consent epoch, settings hash and the original upload deadline. Capture duration is5/10/15/20minutes, with a fixed60second upload drain; that drain does not extend the accepted event timeline. Accepted event timestamps must span at most the saved duration, without assuming that the browser wall clock equals the server clock. A restored installation disables replay and rotates the native epoch for **every** replay-configured project, including disabled configurations, so restoring the same signing key cannot revive old capabilities. Re-enabling requires fresh explicit consent; restore does not delete recording history.

`POST /api/replay/chunks` accepts exactly `{siteKey,url,consent,token,sequence,final,data}`. Data is canonical base64url of UTF8 JSON, not HTML. The limits are256KiB decoded bytes/chunk,200event-or-fragment envelopes/chunk,1024chunks and64MiB per recording,4MiB per reassembled event,64fragment parts/event, JSON depth64 and20000structural nodes per decoded tree. HTTP bodies are bounded before parsing. Each chunk hashes its exact decoded bytes, sequence and final flag; exact retries are idempotent, changed bytes/final/sequence conflict, and rejected chunks leave no partial insert/counter update.

The closed event envelope permits rrweb lifecycle/meta/snapshot/incremental types0–4, bounded timestamps and untrusted JSON data. Plugins/custom events are excluded. Meta is a closed query-free same-origin URL and viewport object; full snapshots require serialized nodes; incremental sources are bounded. Fragments are closed UUID/index/total/base64 envelopes. The server indexes affected fragment IDs and validates newly completed groups on every upload, even before a final chunk arrives. A fragmented foreign/excluded Meta, conflicting parts or oversized event cannot become readable through partial uploads. Node data remains **untrusted content**; these checks are not an HTML sanitizer or input-masking guarantee.

Out-of-order sequences are accepted within the fixed limits. Complete requires a final sequence, every sequence0..final, every fragment group, and both Meta/full snapshot. Missing final/chunks/fragments stay explicit; capacity/validation refusal must never be presented as a complete recording. An incomplete recording can expose its accepted bounded chunks, but the player must not invent missing events. The assembled order follows chunk sequence and first fragment position.

## Dashboard reads

Cookie-only GET routes are `/api/projects/:project/replays`, `/:recording`, and `/:recording/chunks`. Current owner/admin/editor/viewer membership is checked after the workspace lock. Analytics bearer keys cannot read replay DOM, even with `analytics:read`. Responses are no-store, capped at2MiB, with5second SQL/lock limits. List pages contain20recordings plus a bound cursor; native timestamp anchors preserve microsecond ties. Pages are live keyset pages, not a frozen database snapshot. A removed/purged cursor requires a fresh list.

Chunk pages contain at most4ordered typed chunks and `nextAfter`; the only chunk query is one canonical numeric `after`. Detail permits no query. Metadata and chunk page are read in one SQL snapshot. Completeness/counts cannot be mixed from a concurrent upload generation. The saved settings identify how a future player should interpret masking, not proof that masking occurred.

The default replay policy is7days, independent of analytics traffic. Reads use a fresh SQL clock and native-precision cutoff after current authority locks. Expired recording content is immediately unavailable; the point DTO marks expiry, sets entryPath to null, redacts counts/sequence and returns no chunks while physical deletion catches up. A replay retention watermark is monotonic, including an atomic old/new minimum latch on policy save; extending retention cannot revive data already excluded by that watermark.

The existing worker clears at most1000expired paths, deletes32chunks (at most8MiB payload), clears at most1000chunk-free metadata counters/timestamps, and deletes at most1000expired request tombstones per project pass. Safe IDs/request hashes/origin/settings/deadlines remain as expired tombstones under the existing derived-history policy(default365days), at least as long as the raw replay period, to prevent a lost Begin ACK from recreating purged content. Tombstones retain no recorded path or events. An expired same-key retry conflicts; it never renews the old capability. This is a bounded retention window, not permanent request-key storage. The worker cannot mark a pass complete while required raw cleanup or expired tombstone deletion remains. Preview reports actual affected replay metadata/chunk row counts, a10000row lower-bound sample, logical stored row bytes and explicit unavailable estimates on timeout. No replay ingestion emits analytics events, creates visitor identities, starts queues or spends provider funds.

## Pinned browser asset and isolation

Paused seeks include all events at the requested millisecond, including the final event and events sharing its timestamp. The adapter compensates for pinned rrweb2.1.7's exclusive seek boundary internally; displayed position and recording duration remain unchanged. Recorded viewport changes also update the preview scale without waiting for the surrounding window to resize.

The self-hosted `/replay.js` embeds the unmodified rrweb2.1.7 UMD build and this application's adapter. The registry archive integrity, exact upstream commit, bundled dependency licenses and full notices are recorded in `THIRD_PARTY_NOTICES.md` and `public/vendor/rrweb-LICENSE.txt`. Native controls use core Replayer; no separate alpha player UI is installed. Following rrweb-player and Umami 3.4.0, playback offers 1×/2×/4×/8× and skips inactive periods by default, with a visible notice and a toggle; both choices last only for the open preview. They cross the MessagePort as the closed `replayPlaybackOption` messages, which the adapter checks again and otherwise ignores. Primary sources: [rrweb repository](https://github.com/rrweb-io/rrweb), [registry metadata](https://registry.npmjs.org/rrweb), and [rrweb guide](https://github.com/rrweb-io/rrweb/blob/main/guide.md).

The trusted player wrapper uses a generated `data:text/html` URL, which has its own opaque origin, with `sandbox="allow-scripts allow-same-origin"`. The token retains that opaque origin; it does not give the frame the application's origin. The wrapper can therefore access rrweb's nested `about:blank` document, whose sandbox remains exactly `allow-same-origin` with scripts disabled. A forced-origin `srcdoc` sandbox would give that nested document a different opaque origin and prevent rrweb startup. See [data URL origins](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/data) and [HTML sandboxing](https://html.spec.whatwg.org/multipage/browsers.html#sandboxing).

The wrapper accepts recording data only over its parent-bound MessagePort. Its nonce-only script policy, disabled connections/workers/forms/objects/media, restricted images and frames, and no-referrer policy apply independently of the nested script-disabled sandbox. Recorded DOM is never interpolated into wrapper HTML. No login credential or upload capability enters playback. Canvas/cross-origin iframe recording and unsafe canvas replay remain disabled. Actual hostile-DOM/network checks must verify both frames cannot access the application, while the trusted wrapper can access its own inner replay document; a synthetic player peer cannot establish this guarantee.

Recording data loads only after an explicit action, in sequential four-chunk pages with progress and cancellation. Each read has a15second deadline; an operation has120seconds. A rate refusal or overall deadline pauses at the verified cursor without automatic retry. Explicit Resume loading continues the same recording generation under the unchanged60reads/user/minute cap. A changed generation or lost authority clears retained content. Incomplete recordings can preview only a contiguous, fully reassembled prefix with Meta and a full snapshot; the UI never invents missing content.

## Checks

`tests/session-replay.test.ts` covers closed opt-in/settings, canonical UTF8/JSON bounds, Unicode fragment ordering/conflicts, completeness and reassembly limits. `tests/session-replay-integration.ts` contains8whole groups using actual SQL/API/normal owner-cookie authentication: disabled defaults, concurrent persisted sample/deadline, exact chunk retries/caps, fragment paging and nonfinal origin/duration refusal, privacy/publication lock races,4roles/foreign/API-key/held membership refusal, post-lock capability replacement/body/CORS, and actual7day preview plus32+8chunk deletion. Existing restore checks retain financial/CLI oracles and add old-capability/fresh-consent cases.

`tests/session-replay-browser.mjs` exercises the component with synthetic API responses and a synthetic player peer. `tests/session-replay-vendor-browser.mjs` separately exercises the shipped real recorder/player; only configuration, Begin decisions and ingress acknowledgements are synthetic, and its hostile-input and adapter-seam lanes are explicitly labelled. These checks are separate from compiled application, live-provider, real browser-history restoration and deployment acceptance. Passing one lane does not imply the others passed.
