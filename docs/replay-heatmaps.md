# Saved replay metadata and independent heatmaps

Migration0056 registers saved recording metadata and independent numeric heatmap storage after the replay55 prefix. This code reference describes the implemented contracts; acceptance evidence and the remaining feature roadmap live in Docmost. The private0059 successor below adds historical background references; it remains unregistered and unexecuted until review and the actual0057/0058 prefix. Source authoring is not full visual heatmap acceptance.

## Saved recordings

Cookie-authenticated owner/admin/editor can save, rename and unsave a recording; all four current workspace roles can read. API keys and public shares do not gain access. `GET /api/projects/:project/replays/saved` accepts one optional literal `search` (100 characters) and scope-bound cursor; live pages contain20 items plus a sentinel. Ordering uses immutable recording `(created_at,id)` and native timestamp anchors, so unsaving the previous page's last row does not discard the next page. This is not a cross-page snapshot.

`GET /api/projects/:project/replays/:recording/saved` returns `{role,asOf,item,saved}`. `item` is the unchanged P41 recording DTO; `saved` is `{name,revision,savedAt}` with nullable name/time. Existing P41 list/point/chunk response shapes are unchanged.

`POST` to the same point path accepts exactly `{requestId,revision,action,name}`. Actions are `save`, `rename`, `unsave`; only unsave requires null name. Revisions start at0 and never cycle after unsave. Exhaustion refuses a new organizational write. The atomic receipt is bound to actor, project, recording and normalized exact input. ACK is `{role,request:{...input,recordingId},appliedRevision,replayed}`; replay returns the original applied revision under current editor authority. A point GET showing the requested state does not acknowledge an unknown write. Clients must retain the original request/body until its exact contextual ACK or explicit abandonment.

Save/rename requires currently retained raw recording. Unsave is allowed on an expired bookmark. Names never extend raw replay retention (default7 days), change capture timestamps, copy chunks or resurrect expired content. Expired raw metadata stays visibly expired; authored saved metadata ends when unsaved or the existing derived recording cleanup deletes its row.

## Numeric heatmap collection

Optional `analytics_settings.heatmap={enabled,sampleRate}` defaults off. Old settings forms omitting it preserve its current value; ordinary Analytics, performance and replay settings retain their old semantics. Heatmaps require explicit current Analytics consent and enabled configuration, independently of replay permission/configuration. Basic/cookieless analytics does not authorize this dataset.

`POST /api/heatmaps/begin` accepts strict `{siteKey,requestId,url,consent:{analytics:true,epoch}}`. It persists a single sample decision, settings binding, exact Origin/path and server clock. Response contains accepted/reason, captureId, token/null, createdAt, deadlineAt, uploadUntil, settings and limits. The capture is fixed at5 minutes with60 seconds to drain; retries do not extend it. Purpose-separated HMAC capabilities bind project, exact origin, capture, epoch, settings and expiry. Expired old batch capabilities cannot recreate data after purge. Begin tombstones have the existing derived-history lifetime; replaying an old Begin after its tombstone was deleted is a new Begin, not permission to reuse its old upload token.

`POST /api/heatmaps/batches` adds requestId, captureId, token, one geometry and1–20 observations, at most32768 UTF-8 bytes. Each capture accepts at most256 batches and8MiB. Exact request/hash retry has no count inflation; changed-body reuse409. New offsets are monotonic and bounded0–300000 milliseconds, independent of client wall-clock time. Every Begin/upload rechecks current Origin/site/epoch/settings, explicit consent, path exclusions, bots, DNT and GPC after the publication lock. No event/visitor rows, identity linking, provider charges, jobs or replay vendor calls are produced.

Proposed versioned geometry contains only `basis:'document-css-v1'`, direction, pageWidth/pageHeight and viewportWidth/viewportHeight. Each click carries document x/y plus native clientX/Y and scrollX/Y at that event; each scroll carries its own scrollX/Y. Client coordinates count from the recording window's viewport origin; `document-css-v1` requires that origin to be client (0,0), which holds for a top-level Chromium/Edge document even with a classic RTL scrollbar (drawn on the right there). Static extents/direction define cohorts; changing scroll position does not. A resize/document growth requires splitting batches. Numeric validation is not proof of a native coordinate transform: actual RTL, horizontal scroll, body/html zoom and visual viewport calibration remains required before a collector is accepted. The server derives each scroll depth from that observation's vertical origin and declared viewport/page heights, never one outer scroll origin for20 events. No DOM, text, selectors, query, input values, keystrokes, raw IP or screen fingerprint is stored.

## Reads, bounds and retention

Cookie-only `GET /api/projects/:project/heatmaps` supports one mode: `pages`, `geometries`, `click`, `scroll`. Dates are inclusive UTC1–366days; pages mode has no page selector, geometries requires exact origin/path, click/scroll additionally require a geometry key. Cursors apply only to live20-item page/geometry lists. Scope and range bind native retained anchors. Reports use a fresh post-authority-lock clock, retained raw rows, a single data statement and a2MiB complete JSON ceiling; statement/lock bounds are5 seconds. Collection paused/off still allows retained reads.

Click reports group exact coordinates, return top5000 groups and disclose exact returned/omitted group and observation counts. Unknown geometry/fully unavailable range uses null counts, not measured zero. Scroll reports count each capture once at maximum observed depth, with10 cumulative depth bands; these are sampled captured documents, not people, sessions or visits. Responsive geometries are never merged into one pretend layout.

Heatmap payloads/path metadata follow rawAnalyticsDays (default90), independently of replayDays. Current policy may reveal still-stored raw rows after extension before cleanup, matching existing analytics semantics. The irreversible analytics watermark and physical deletion prevent later revival. The existing worker deletes at most64 batches (2MiB declared payload) and clears at most1000 capture paths per pass before marking completion; safe Begin tombstones expire under derivedHistoryDays (default365). Preview includes actual batch/path-row logical bytes. Restore disables configured heatmaps and rotates their analytics epoch, including already-disabled settings, without deleting history.

Density coordinates render without replay. The Saved/Heatmaps views and independent collection controls use the existing application routes. Historical page backgrounds require a genuinely matching retained snapshot and must be labelled; no automatic live iframe, server fetch or screenshot worker is introduced. The numeric canvas and readable coordinate table remain usable when historical context is missing. Full visual acceptance additionally requires the actual recorder/player alignment gate below.

## Private0059 successor: retained historical sample

This source draft adds `POST /api/heatmaps/backgrounds` (4096 complete UTF-8 bytes) and cookie-only `GET /api/projects/:project/heatmaps/background`. It does not register0059 ahead of the real0057/0058 prefix. Neither route creates paid work, a job, a DOM copy, a live website request or new retention entitlement.

An upload requires both already accepted, purpose-separated replay and heatmap capabilities, explicit current Analytics plus replay permission, current origin/path/epoch/settings and both immutable upload deadlines. The association references one acknowledged numeric batch of the exact geometry and the actual stored rrweb Meta/FullSnapshot. Direct locators bind sequence, index and stored chunk/event SHA256; fragment locators bind an indexed fragment UUID and the reassembled event SHA256. Resolution reads at most64 affected original chunks per locator (up to16MiB intermediate chunk bytes), at most4MiB for the reassembled event. It never scans a whole recording. The replay offset is derived from the genuine Snapshot timestamp minus the recording's persisted first-event timestamp, rather than a caller-supplied clock origin.

The coordinator measures native geometry in the actual FullSnapshot callback. It keeps only small references, not another serialized document. It attempts a link only after that event's exact parts and a geometry batch have matching ACKs. When an initial snapshot preceded the numeric Begin ACK, or a new acknowledged layout has no anchor, the existing current-owner rrweb `takeFullSnapshot` API is called once for that capture/layout. A late, withdrawn, replaced or expired owner cannot request it. Failed optional link acknowledgments retry the same UUID/body at most once and do not stop independent numeric collection. No earlier recording is backfilled from similar timestamps, paths or dimensions.

One immutable reference exists per capture/layout. Exact request replay returns202 duplicate; changed-body replay or replacement returns409. The original masked replay chunks remain the only DOM storage. The reference contains no upload token, second URL, user identity or raw event body. `observedAt` is explicitly the original browser Snapshot timestamp, not server-attested wall time. `accepted_at` is a fresh post-lock database clock used only to choose the latest available associated sample. A later same-origin SPA Meta/FullSnapshot may be associated with its exact current heatmap path; the recording's initial entry path is not misrepresented as that later path.

Each dashboard page rechecks current workspace membership under workspace/project locks, then one fresh clock for both effective raw retention boundaries. It also compares the original capture/recording epochs; a later publication-epoch rotation does not erase permission to read still-retained historical data. API keys cannot read DOM. The selected exact origin/path/geometry/date range is echoed. At most4 affected original chunks are returned per page, with at most128 referenced chunk sequences and the existing2MiB complete response bound. Missing/expired/incomplete states contain no usable reference, recording or chunk data. A changed sample between pages is rejected by the client rather than assembled across identities.

Loading is explicit. The client follows at most32 four-chunk pages under one current owner/abort scope,120-second whole-load bound and existing per-read deadline; it holds at most32MiB of referenced chunk bytes. It validates scope, immutable reference, order, digests, exact Meta URL and viewport before passing only the two verified events to the existing isolated player. It never automatically loads DOM while the user browses numeric heatmaps. Current401/403/404 or malformed scope purges private observations and the frame; only401 signs out. Other read failures leave numeric values intact. Expiry destroys the frame and does not imply zero recorded clicks.

The player retains its inherently opaque data URL, nonce-only script CSP, no network/worker authority and parent-owned native controls. Optional heatmap mode pauses at the Snapshot, verifies the reconstructed root's exact document/viewport extents and direction, then overlays the selected aggregate in that calibrated plane. It rejects mismatched or changing dimensions instead of guessing a scale. Inside the replay frame a classic RTL scrollbar is drawn on the left and is part of client space, so the player measures where the frame's viewport origin lands (a fixed-position probe, removed before the extent is sealed) and anchors the overlay plane and the extent-restoring marker there, past the iframe's own border, rather than at client (0,0). The same probe spans the frame's initial containing block, which must be exactly the recorded viewport: a frame whose block is narrowed by a gutter reserved behind hidden scrollbars while its clientWidth still matches is rejected as unsupported rather than overlaid with a shifted plane. That origin is a measured DOM fact of the replay frame, not a per-scene constant; `tests/replay-heatmaps-classic-browser.mjs` holds the real-Edge classic-scrollbar scenes. Native scrollbar/withheld-resource differences can therefore make the sample unavailable while numeric coordinates remain usable. LTR/RTL and CSS body/root zoom require actual Edge alignment evidence; the component's synthetic MessagePort fixture is not that proof. A historical sample is one consenting captured document, visibly distinct from all aggregate observations with the same geometry.

References expire under the intersection of current raw heatmap and replay retention. Heatmap batch deletion cascades; the existing bounded worker also removes at most64 references whose source replay/path has expired or been purged. Reading cannot extend either lifetime. Physical purge and existing irreversible watermarks prevent subsequent policy extension, saved metadata or replayed old capabilities from restoring bytes. Current policy may still reveal stored data after an extension before physical cleanup, matching the established retention contract.

## Authored acceptance and qualifications

The private patch preserves the original four pure groups, six numeric VM groups, eight native groups and eleven component-browser groups/counters before additive checks. New checks cover strict dual-capability ingress, direct and fragmented immutable references, actual API202, four cookie roles, bearer denial, held membership/project expiry, physical purge without numeric loss, optional-link unknown outcomes and held UI authority. Native events in those service fixtures are synthetic rrweb envelopes. Component GET bodies and its one player handshake are explicitly synthetic.

The separate actual-browser driver must use the shipped recorder, native trusted input, genuine rrweb callbacks/chunk decoding and the real opaque player to prove overlay alignment. Only configuration/Begin/ingress ACKs may be synthetic there. No source-only test, prior plane calibration or fake player handshake is claimed as completed visual parity. Registration, current type/pure/native/CLI/component/vendor gates and reviewed screenshots remain pending promotion and root admission.
